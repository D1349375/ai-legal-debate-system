## 1. 一句話定位與產品構想

**LegalDebate 是台灣民事案件的攻防預演與爭點整理研究原型：讓原告、被告兩個 AI 角色先各自準備，再交互反駁，由法官角色整理問題，最後留下可查證的分析與書狀骨架。**
它想幫律師在動筆之前看見「對方最強的理由」「自己最薄弱的要件」「還缺哪份證據」。
核心價值假設是：固定的對抗協議與查核紀律，比直接請單一模型整理案情，更容易暴露盲點。
這仍是待專業使用者驗證的假設，不能由少數內部案例直接推出普遍優勢或實務可用率。
書狀初稿是分析流程的輸出之一；產品優先追求爭點與證據準備品質，再追求文字完成度。
目前定位為合格法律工作者監督下的內部輔助工具，不提供一般民眾直接付費代辦訴訟或自動送件服務。
此定位反映專業責任、產出可信度與資料保密需求；本文件不把歷史規劃中的法律評估當成最新法律意見。
「法官」「判決」「verdict」是沿用的程式命名；對使用者應說「爭點強弱評估」，避免誤認為法院裁判或勝率預測。
現階段交付物是可回放的研究原型、確定性工具與測試證據，尚非公開上線的完整律所平台。

### 1.1 為什麼需要雙方攻防

單一回答常直接選一條看似合理的法律路徑，忽略備位請求、時效、證據不足或對方不同的事實定性。
雙方先獨立準備，可保留不同出發點；再強制回應對方，能觀察主張是否因反駁而修正。
要求提出讓步條件，能把「我很有信心」改成「若哪項事實被證明，我必須改變結論」。
但多角色不保證多觀點：若共享同一模型與材料，仍可能一起犯錯，因此引用查核與外部驗證不可省略。

### 1.2 成功應如何判斷

- 律師能指出至少一個原先漏看的重要爭點，或少花時間確認一項風險。
- 分析能回到具體事實、證據與來源，不能只看篇幅長短或法律術語數量。
- 對抗流程若沒有比「單一 Agent＋檢索＋批判查核」更有用，應縮減流程或重新設計。
- 使用者回饋、耗時、模型用量與錯誤率要一起記錄，不能只報正面案例。

## 2. 使用者、場景與完整例子

### 2.1 優先使用者與非目標

| 對象 | 可測試的價值 | 現階段限制 |
|---|---|---|
| 執業律師／法律事務所 | 開庭前攻防、起草前爭點盤點、引用複核 | 尚待正式設計夥伴試用 |
| 實習／初階法律工作者 | 觀察主位與備位論證、整理應補證據 | 必須有專業覆核 |
| 法律系學生 | 理解介面與對抗思考、提供概念回饋 | 不能代替律師效用驗證 |
| 一般民眾 | 可觀看研究展示 | 非自助訴訟代辦與正式法律服務目標 |

第一個實驗場景應限定一種熟悉案類，以已去識別化或公開材料測試，避免同時擴張刑事、家事與行政事件。
目前固定流程針對民事通常訴訟的研究模擬；不代表已涵蓋所有程序門檻、例外與法定期間。

### 2.2 假設案例：公司間貨款爭議

以下為教學假設，不是真實案件結論，也不使用真實公司身分。
甲公司主張已交貨，乙公司尚欠款；乙公司主張部分商品有瑕疵，且雙方曾談過減價。
律師先提供案情、契約、交貨與付款的已知事實，另外標出尚待確認的資訊；不能讓模型補造缺漏。
原告角色列出請求付款可能需要的要件與證據；被告角色列出瑕疵、抵銷、履約與時效等候選抗辯。
法官角色從雙方正式輸出找出真正分歧，例如「是否驗收」「何時通知瑕疵」「是否確有減價合意」。
第二階段雙方回應訊問與對造摘要，第三階段收斂主位、備位與讓步條件。
程式彙整兩方的讓步條件、引用變化，獨立查核角色確認最終引用的來源與相關性。
律師最後看到爭點排序、應補文件、可用與不可用引用，以及待人工審閱的骨架稿。

### 2.3 商工查核在例子中的位置

目前可另外輸入乙公司的統編，核對登記名稱、公司型態、登記狀態、地址與代表人資料。
若登記狀態異常，規則模組產生程序查核提示；若地址可對應法院，提供一般管轄候選與條件。
**這些結果目前只進入當事人查核區與書狀資料卡，不會自動重跑既有攻防或改寫已存的論證。**
未來可將經確認的登記事實轉成「應先查清當事人與代表權」的爭點，但不能由登記異常直接推定欠款成立。
例如「公司現在解散」不代表締約時已解散、不代表負責人個人應賠償，也不代表公司債務不存在。
這個由公示事實到程序問題、再到個案論證的界線，是下一階段最重要的產品設計。

## 4. 端到端流程與角色

~~~mermaid
flowchart TD
  A[人工確認案件輸入] --> B[雙方 Stage 1 獨立準備]
  B --> C[法官整理爭點與訊問]
  C --> D[雙方 Stage 2 回應與反駁]
  D --> E[雙方 Stage 3 收斂與讓步條件]
  E --> F[純程式彙整弱點與引用位移]
  F --> G[法官爭點強弱評估草稿]
  G --> H[獨立引用查核與人工相關性覆核]
  H --> I[查核通過後落地與書狀骨架]
  J[商工查核] --> K[當事人與書狀資料卡]
  K -.未來經確認才納入新一輪分析.-> A
~~~

目前完整生成流程由 [.claude 編排說明](../.claude/skills/legal-debate/SKILL.md) 驅動外部 Agent 執行。
Python CLI 與 FastAPI 本身沒有呼叫 LLM 生成攻防的功能；不要把上圖誤讀為按一次 UI 就會全自動跑完。
編排者透過案件 JSON、角色輸出 JSON 與 CLI，把各步資料寫進 SQLite。
UI 讀取這些紀錄並重播；機械彙整、引用查證與商工資料查核則可在目前介面上實際執行。

### 4.1 十步流程與資料產物

| 步驟 | 責任者 | 輸入 | 輸出／關卡 |
|---|---|---|---|
| 1 | 人＋編排者 | 案情、請求、案類 | Case JSON、雙方立場詞 |
| 2 | 原告／被告各自 | 相同案件、各自任務 | 兩份 Stage 1，互不見對方內容 |
| 3 | 法官角色 | 雙方 Stage 1 正式輸出 | 有 based_on 的訊問、暫存無爭議點 |
| 4 | 雙方各自 | 自己全文、對造摘要、法官訊問 | Stage 2、falsifier |
| 5 | 雙方各自 | 自己上一輪、對造摘要 | Stage 3、最終候選與 falsifier |
| 6 | aggregate＋DB | 雙方 Stage 3 與 Stage 1 | weak_points、position_drift |
| 7 | 法官角色 | 正式三階段紀錄、機械錨點 | 尚未落地的爭點強弱評估 |
| 8 | 獨立查核角色＋工具 | 引用清單、必要原文 | 存在查核，最終採用引用另覆核相關性 |
| 9 | 編排者＋骨架規則 | 通過查核的分析與引用 | 書狀骨架，CLI 再檢查引用狀態 |
| 10 | 人＋編排者 | 全部產物 | 回報爭點、限制、補證建議與草稿 |

無爭議點目前沒有獨立資料表；編排者需保留它們，不能宣稱所有法官中間輸出都已結構化保存。

## 5. 攻防協議與檢索

### 5.1 Stage 1：先保留不同路徑

原告與被告各在獨立上下文中準備，先不讀對造輸出。
提示模板要求列出可能的請求權基礎或抗辯，逐項檢驗要件，再處理對方反駁與備位方案。
同一案件有多筆金額或不同法律關係時，應分項分析，避免打包成單一結論。
輸出為 position、reasoning、cited_statutes、cited_precedents 等欄位；案件、角色與階段由編排落地時帶入。
這是任務與上下文安排的隔離，不是資料庫層多租戶安全隔離，也不是三套已獨立部署的模型服務。

### 5.2 Stage 2：面對反駁，不互相抄全文

每方讀自己的完整上一輪、對造的結構化摘要與法官訊問。
摘要只含對造立場、最強論點摘要與引用，刻意減少全文語氣與敘事互相污染。
雙方應重新檢查候選路徑，逐則回應訊問，判斷主位受挫是否啟用備位。
新增的內部一致性檢查，要求不同候選與不同輪次之間不要自相矛盾。
Stage 2 與 Stage 3 的 falsifier 在 DB 寫入層為必填，不能用空白繞過。

### 5.3 Stage 3：收斂，不無限加輪次

雙方盤點哪些候選仍成立、哪些受挫、哪些未經檢驗，再決定最終主位與備位。
不因模型「還能再講」而增加輪次；固定協議讓案例、成本與版本比較更有意義。
法官最後接收的是正式輸出與機械錨點，目標是排序爭點與補證方向。
目前「不得違背錨點」主要靠提示與事後一致性顯示；DB 沒有完整判斷自由文字是否語意矛盾。

### 5.4 檢索的現況與未來設計

[stance_rag.py](../engine/stance_rag.py) 只提供 build_stance_terms，不讀文件、不呼叫模型、不建向量索引。
通用原告詞偏向請求權成立、應給付、責任；被告詞偏向時效、抗辯、欠缺基礎。
侵權、契約不履行、勞資爭議有額外詞；未知案類回退通用詞，不代表案類已全面支援。
實際查找由 Agent 使用檔案檢索工具對本地法規與裁判資料執行。
模型自己的法律知識只能產生「候選引用」；沒檢索命中不等於假的，檢索命中也不等於適用。
向量檢索、SAC、重排序、法官爭點統計層及工具權限私有切面，目前仍屬設計規格，不能列為已完成。
是否建向量層，應先量測現行檢索的漏查、錯文件、雜訊與延遲；避免只因文件有 RAG 字樣就擴張工程。

## 6. 機械彙整與引用閘門

### 6.1 弱點彙整究竟計算什麼

[aggregate.py](../engine/aggregate.py) 是不碰模型與資料庫的純函數。
compile_weak_points 收集 Stage 3 的 falsifier 與 reasoning 摘錄，依固定規則排序。
它不理解法律要件、不重新裁判證據，也不自動選出「勝負機率最高的兩點」。
disagreement 用 Stage 1 與 Stage 3 的引用集合計算 Jaccard 距離：

~~~text
position_drift = 1 - |初始引用 ∩ 最終引用| / |初始引用 ∪ 最終引用|
~~~

兩集合皆空時為 0；某方缺少其中一階段時為 None；數值四捨五入到四位小數。
這是引用依據變化的代理指標，不是語意立場移動、辯論品質、共識程度或勝率。
只改文字而引用不變，指標可為 0；增加不相關引用也能提高數值，因此不能當排行榜目標。

### 6.2 三層查核應分開說明

| 層次 | 要回答的問題 | 目前能力 |
|---|---|---|
| 來源存在與身分 | 該條文／裁判字號是否在支援範圍內可找到？ | Python 查證工具與來源連結 |
| 內容支持 | 原文哪個段落支持這個命題，是否斷章取義？ | 編排要求獨立角色讀原文；尚無完整結構化程式保證 |
| 個案適用 | 本案事實與要件、時間版本、證據是否相符？ | 待律師覆核，非 published 自動保證 |

[verify.py](../engine/verify.py) 目前解析六部法律的名稱與別名：民法、公司法、勞動基準法、消費者保護法、刑法、民事訴訟法。
本地完整法典檔為前五部；民事訴訟法可即時查條文，不等於已有完整本地副本。
其他法律、其他法院、各種引用寫法與歷史版本均未全面涵蓋；未知格式不可偷偷放行。
條號支援「第 191 條之 2」與連字號子條；引用身分正規化不等於已逐項核對條文項、款與生成引文。

### 6.3 法規、裁判與離線行為

法規查全國法規資料庫的指定條文，取得官方文本與 URL；程式沒有逐句核對生成文字是否忠實引用。
法規連線失敗時，UI 可顯示本地法典快取，但標 local_cache_only 並阻擋，不冒充本次官方查證。
最高法院民事裁判先依 TPSV 檔名的年度、字別、字號查本地官方資料語料；命中可標 published。
未命中才查 FJUD；精確比對裁判身分，區分查無與連線失敗，不能把相近字號當同案。
本地裁判命中是既有官方來源副本的身分比對，不代表當天重新查官網或已讀全文判斷支持性。
UI 的 previous_record、recorded_check 與本次 status 分開呈現；不能用過去成功結果遮蓋本次失敗。
離線模式下，本地裁判仍可能通過；「離線一律不能 published」也是不精確的說法。

### 6.4 DB 機械閘門與仍待補的缺口

record_verdict 與 record_pleading 檢查呼叫端傳入的 citations_used，只要有未 published 的引用就拒絕。
案件、同一角色同一階段的論證、最終評估不可覆寫；書狀草稿可追加版本，兩者規則不同。
閘門不會完整抽取正文全部引用；呼叫端若漏列引用，現有 DB 無法自動知道，空清單也會通過。
UI 有正文引用的事後重解析，但受目前正規表示式範圍限制，不能取代寫入前完整一致性驗證。
upsert_citation 接受呼叫者傳入的狀態；註解中的「任何編輯強制重設 draft」並非完整的逐欄防護機制。
未來要把來源身分、原文片段、支持命題、審核狀態與正文引用一致性分別落地，不能讓單一 published 承擔全部意思。

案件輸入檔存在但 DB 沒有論證時，介面顯示 input_only，不補造辯論或評估。
錄製案件從 demo/recorded_cases.json 匯入空 DB；商工錄製資料與先前查證紀錄各用獨立 fixture。
目前沒有 case_runs、模型呼叫追蹤、完整證據庫、使用者權限、完整工作階段版本與多租戶資料分離。
核對時本地語料有五部法典全文與 1,088 份最高法院民事裁判；來源 JSON 記錄取得路徑與部分日期，不代表目前仍是最新版本。
已有[裁判種子擷取腳本](../scripts/fetch_judgments.py)與[月封裝匯入腳本](../scripts/import_monthly_judgments.py)，主要用於初期建庫；持續同步與異動移除仍需另行設計。

## 9. 開放資料整合現況

### 9.1 整合目標

商工資料用來減少當事人身分誤植，補足「列誰、誰代表、送哪裡、還要查什麼」的程序準備。
目前以固定程式把公示欄位轉成提示，不把原始商工資料直接送給 LLM 生成新法律結論。
設計把輸入、官方回應、轉換規則、提示與來源分開，避免名稱錯配或資料缺漏被模型補成看似完整的事實。

目前公司型態以名稱尾綴、狀態與外國公司名稱規則推定，應視為輔助分類，不能取代原始登記文件。

### 9.4 程序警示、代表人、管轄與書狀卡

party_rules 的提示涵蓋名稱不一致、代表人不一致、解散／廢止／撤銷、合併、破產、清算完結、停業、商號與外國公司。
每則提示有 code、level、message、legal_basis；規則是可測試的條件轉換，附法條也不代表已覆蓋全部例外。
股份有限公司僅在登記負責人與董監事董事長吻合等條件下自動提供代表人；資料缺漏或不一致時保留待確認。
有限公司、外國公司、清算與破產等情境有不同路徑，不可用單一「負責人＝法定代理人」填滿全部案件。
主體為分公司統編時，現功能未抓該分公司完整基本資料，不自動帶名稱、地址與代表人，提示改查總公司。
court_map 由地址提供一般法院候選；有些地區需行政區辨識，有分公司時另列「因其業務涉訟」等條件。
輸出應是候選與待確認事項；約定管轄、專屬管轄、消費與勞動等特別規則不能由地址表全面解決。
書狀分頁的當事人資料卡顯示最新查核摘要與來源；**它不改寫既有 draft_text，也不把登記資訊插入已存論證。**

### 9.5 查詢、資料血緣與儲存

gcis._query 以標準庫 HTTP 呼叫官方 JSON API，URL 帶資料集、filter、skip、top，預設每請求六秒。
client 回傳 ok、rows、url、fetched_at、error、dataset；成功空陣列和連線錯誤是不同結果。
服務層把各來源組成 sources，保留各自 URL、取得時間、成功與錯誤；部分來源失敗不覆蓋其他來源成功資料。
標準化摘要包括 ban、entity_type、name、status_text、company_form、代表人、地址、警示、管轄與資料來源。
party_checks 保存 result_json 與 raw_json、case_id、role、query_ban、input_name、via、fetched_at、created_at。
查詢採追加紀錄，不改舊快照；API 依案件與角色讀最新紀錄，但「最新」仍可能是錄製回放，必須看 via。
目前沒有每個標準化欄位的 JSON Pointer、原文雜湊、規則版本與欄位級有效期間，這是下一階段的血緣缺口。
程序警示內的法條可在 UI 另按查證，不是每次商工查詢都自動完成法條查核；警示文字仍需依適用時點覆核。
fetched_at 是取得時間，created_at 是落地時間，都不能直接當成登記事實的生效時間。

### 9.6 失敗、部分成功與錄製回放

| 情況 | 現有行為 | 展示與後續分析要求 |
|---|---|---|
| 類型查詢失敗 | unresolved／failed | 不說查無，不自動推當事人不存在 |
| 主資料請求失敗 | failed | 附其他已取得來源，提示欄位未完成 |
| 類型存在但基本資料空白 | partial 與缺漏說明 | 不補造名稱、代表人或地址 |
| 董監事／分公司單獨失敗 | partial | 不把未取得代表資訊當已確認 |
| 官方確認沒有主體 | not_found | 與網路失敗分開，仍允許核對輸入 |
| 全部本次請求失敗且有相同統編錄製資料 | recorded，保留本次 live_attempt | 明示歷史取得時間與非本次即時查詢 |
| 名稱搜尋失敗／無候選 | 顯示失敗或空清單 | 不等於任何狀態的同名主體都不存在 |

錄製回放是 demo 可重現措施，不是正式服務的自動更新快取；目前沒有完整 TTL、背景更新與衝突解決策略。
回放會以目前規則重新摘要，停業判斷仍使用執行當日，不能把這種回放視為完整還原原查詢日的法律或營業狀態。
若部分成功，不會任意把失敗欄位用歷史值混補；未來若做混補，必須逐欄標示來源與不同時間。
資料提供機關、實際用到的資料集與授權連結需跟著畫面與匯出物保留。[政府資料開放授權條款](https://data.gov.tw/license)

### 9.7 官方平台限制與時間版本

依 2026-10-27 查核的 [商工開放資料開發指引](https://data.gcis.nat.gov.tw/od/rule)，部署前需確認介接告知、外部 IP 白名單及連線／每日用量規則。
目前程式沒有 API key 欄位，不表示任何網路環境都無須申請；現場與部署主機的外部 IP 都應事先驗證。
官方平台可能回傳非授權 IP 或非陣列錯誤訊息，現 client 會視為回應錯誤，後續應提高錯誤分類可讀性。
六個資料集目錄更新頻率列為「不定時」，董監事描述另提每小時；不能統一宣稱即時更新或保證 SLA。
商業應用三的官方說明含現況及歷程，但本實作只取首筆，沒有歷史排序與案件時點還原。
總公司分公司清單最多五十筆、董監事最多一百筆、名稱候選最多十筆，沒有完整分頁擷取。
分公司 count 是已取回筆數，非官方總數；達五十筆時有截斷提示，董監事目前未設相同截斷旗標。
未來部署還要增加節流、重試與退避、查詢預算、來源條款追蹤；目前不宜假設無限查詢與固定可用性。

此啟動流程不需付費模型呼叫，也不會即時生成新的攻防；執行生成需另具 Agent runtime 與使用額度。

污染案例、執行失敗與反例都保留，不能只挑好看的案件；先凍結測試集再改 prompt。
來源存在率與重要爭點命中率分開計算；生成一百筆易查引用不應提高法律實用分數。

## 13. 從登記查核走向爭點推演

本節全部是**建議設計與待辦**，不屬於目前程式已支援的 API 或 DB 欄位。
目標不是再多串幾個資料源，而是讓每一項可用資料都能轉成可反駁、可覆核的問題，維持來源與法律推論分層。

### 13.1 新增資料如何進入案件

~~~text
官方回應 → 原始快照 → 欄位正規化 → 人工確認主體與案件時間
         → 登記事實包 → 程序爭點候選 → 雙方獨立攻防 → 查核與律師覆核
~~~

不能從 API 回應直接跳到「被告應負責」；中間必須保留主體對應、時間、缺漏與確認紀錄。
第一版只做程序問題：當事人列法、代表權、送達地址與一般管轄待查；實體責任需案件證據才可分析。
以同一份經確認的公示事實包給雙方，雙方只分開主張與法律解釋，避免把共同事實也藏成不對等資料。
當事人的私有陳述與未公開策略另有權限規則，不與公示登記資料混在同一欄位。

### 13.2 建議資料契約

~~~json
{
  "schema_version": "legaldebate.registry-facts/1",
  "case_id": "demo-company-dispute",
  "case_run_id": "run-002",
  "party_ref": "defendant-1",
  "entity": {"ban": "00000000", "name": "教學示意公司", "kind": "company"},
  "identity_review": {"status": "pending", "confirmed_at": null},
  "case_event_date": "2024-06-01",
  "snapshot": {
    "source": "GCIS",
    "dataset_id": "API-ID",
    "source_url": "official-query-url",
    "retrieved_at": "2026-10-27T00:00:00Z",
    "effective_at": null,
    "raw_sha256": "待計算",
    "mode": "live",
    "query_status": "ok",
    "ruleset_version": "party-rules/待指定"
  },
  "facts": [{
    "fact_id": "registry-fact-1",
    "field": "registration_status",
    "value": "解散",
    "source_pointer": "/0/Company_Status_Desc",
    "temporal_scope": "snapshot_only",
    "review_status": "pending"
  }],
  "missing_fields": ["liquidator"],
  "conflicts": [],
  "accepted_for_reasoning": false
}
~~~

00000000 僅為格式示意，不應拿去當有效主體查詢；目前八位數驗證只驗格式，之後仍會做官方類型與精確統編查核。
現有流程尚缺案件主體對應與人工確認紀錄；此契約補上這層確認，不把輸入格式正確視為當事人已確認。
fact_id 應能連到原始快照與欄位位置，摘要不能只留「AI 認為公司已解散」。
effective_at 無資料就保持空值，不以 retrieved_at 或 Change_Of_Approval_Data 硬填。
確認主體時記錄統編來源、操作者與確認理由；名稱候選未確認前 accepted_for_reasoning 一律 false。
正式版應保存操作者身分與權限，但公開展示資料須去識別，避免輸出個資。
同一查詢的成功、部分失敗、回放模式與原始錯誤均保留，未確認資料不得因畫面需要而自動升級信任。

### 13.3 程序爭點契約

程序爭點候選建議欄位為 issue_id、issue_type、party_ref、fact_refs、legal_basis_refs、hypothesis、required_evidence、review_status。
例如 hypothesis 是「目前資料顯示可能涉及清算，應確認本案代表權」，不是「原告必定應改告清算人」。
required_evidence 可列公司變更登記文件、法院相關資料、合約與涉訟時間，並註明目前尚未取得。
每個候選需列出能推翻它的條件：例如登記時點晚於案件事件，或已有合法另選代表人的證明。
Agent 可提出補證與備位論證，但不得把登記提示當成已查證的責任結論。
法官角色應把未決程序問題與實體請求分開排序，避免因形式風險把實體爭議直接判輸。

### 13.4 證據優先順序與衝突處理

針對登記事實，先核對官方原始文件／快照，再看可追溯標準化欄位；人工與模型摘要不能無理由蓋過原始資料。
針對交易事實，契約、往來、交付與付款等案件證據優先處理，GCIS 只補主體公示背景。
資料來源的權威性不表示它能回答所有法律問題；官方登記也不會自動證明違約、故意、損害或因果關係。
針對法律結論，應確認適用時點的法規、裁判論理與個案要件，不能用單一來源等級排序取代法律判斷。
若兩來源姓名或地址不一致，保留雙值、日期與來源，要求確認，不自動取字串較長或較新的那筆。
現在的代表人不一定是締約或訴訟中某時點的代表人；應把「現在」與「當時」分開提問。
歷史資料查不到時輸出「無法還原」，不能把目前狀態倒填歷史；也不能將公司與自然人責任混同。

### 13.5 新資料與舊攻防的版本關係

目前 write-once 的論證應保留；整合資料後以新 case_run_id 重跑，不就地改寫舊結論。
現 DB 尚無 case_run_id，第一階段可用不同 case_id 明確分版，後續再做正式 run 模型。
run 應凍結事實包、來源快照、規則／prompt／模型版本、機械錨點與審核紀錄。
新舊結果比較至少指出：新增哪個登記事實、改變哪些問題、哪些結論沒改、是否增加不必要的誤報。
資料卡更新與推理更新是兩件事；UI 應能顯示「查核資料較新，分析仍基於舊快照」，避免靜默混用。

### 13.6 後續資料源選擇

先把既有商工、法規與裁判的血緣和日期做好，再評估增加官方歷史登記、代表權或清算相關可合法取得的資料。
每新增一源先寫清楚：解決哪個爭點、可用欄位、授權、取得方式、更新、缺漏、身分鍵與時間語意。
需登入、申請、人工取得或未確認存在的資料，不應在展示中寫成可自動查詢的既定 API。
避免以廣泛蒐集個人姓名建立關係圖取代案件需要；新來源應有最小必要範圍與保留期限。
若資料不能降低錯誤或減少使用者確認成本，即使容易介接也可暫緩。

### 13.7 法規與裁判的背景同步

這是後續資料維護線，與現在使用者按下按鈕的法規／FJUD 身分查核分開；現有建庫腳本不等於已完成背景同步。
法規可評估[中文法律資料檔](https://data.gov.tw/dataset/18289)與[中文命令資料檔](https://data.gov.tw/dataset/18290)，兩者位階與範圍不同，不能只下載法律就宣稱涵蓋施行細則。
官方目錄提供異動、生效、生效內容、廢止與沿革等欄位，更新頻率列每月；這不是逐條歷史版本都已完整還原的保證。
同步時保留原始包、下載時間與雜湊，建立法規識別碼、條號、版本、生效／失效範圍與沿革關聯；查不到完整有效期間就留空並標示待確認。
案件引用應鎖定事件時點適用版本；法規更新不能靜默改寫舊 run，應標示需重新覆核並產生新版本。
裁判背景同步應依[司法院裁判書開放 API 規格，114.08.22 版](https://opendata.judicial.gov.tw/api/Newses/42/file)：以申請帳密換 Token，Token 有效六小時，服務時段為每日凌晨 00:00–06:00。
官方所述異動清單是「7 日前」的異動，例如 10/16 取得 10/9 的異動，不是任意歷史全文搜尋，也不能當成當天即時更新。
現有種子腳本註解把它描述為近七天異動；正式同步前需依官方規格與實際回傳校正，不能照舊註解承諾覆蓋範圍。
同一 JID 再取得時應以新內容更新；官方表示裁判移除或不再公開時，須刪除先前取得內容，並同步處理檢索索引、快取與公開展示副本。
為兼顧紀錄與移除要求，可留不含正文的移除事件與失效引用標記，不以「保留歷史」為由繼續公開或檢索已移除正文。
目前月封裝匯入會跳過已存在 JID，種子腳本亦無完整移除與同步游標，尚不符合這套持續維護目標。
第一版驗收至少測試同 JID 更新、移除、Token 過期、服務時段外、缺漏日期補取與中斷恢復；帳密不可寫入 repo 或執行輸出。
與既有 FJUD 網頁查核的關係是：背景管線維護本地語料，互動查核確認候選來源身分；兩者都不能自動證明判決內容支持個案論點。

## 14. 工程限制與設計取捨

| 取捨 | 現階段理由 | 何時重新檢視 |
|---|---|---|
| 單一模型、多角色 | 先驗證協議，降低模型變因 | 專業盲測顯示嚴重同質化 |
| 固定三輪 | 可比較、可控成本 | 有實測證據顯示某案類需別種流程 |
| 關鍵字檢索先行 | 語料與 MVP 不必先建完整向量層 | 有量測證明漏查或錯配是主要瓶頸 |
| SQLite＋原生 UI | 本機一個程序即可展示 | 多人並行、權限與持久任務成為實際需求 |
| 確定性規則處理登記 | 可稽核，避免模型補造公示事實 | 規則維護成本增加時仍先保留可解釋性 |
| 書狀骨架先於文風蒸餾 | 真實訴狀語料與專業驗證未備妥 | 取得合法可用語料與律師審閱 |
| 重播＋即時機械操作 | 展示已完成流程且降低現場模型變因 | 完成可靠的生成執行服務與成本驗證 |

模型上下文隔離、提示規則與機械閘門各管不同事情，不能把其中一個當成全系統安全保證。
現有系統沒有完整的背景任務、斷點恢復、取消、重試冪等、模型金鑰管理與費用上限機制。
外部網站 HTML／欄位可能變更；需契約測試與失敗提示，不能把歷史連線成功視為長期可用。
目前沒有可靠的單案 token／時間／費用全鏈路測量；舊規劃的粗估不能直接當現在單價。
蒸餾語料、檢索語料、評估集應分開；公開判決可能進入預訓練，僅移出本地檔不能完全防污染。
更大工作流平台、案件管理、全球法域與商業定價均非此階段已驗證需求，不應拿來承諾團隊交期。

## 15. 團隊分工與敏捷流程

### 15.1 兩人與 AI 的建議分工

| 角色 | 人的責任 | AI 可協助 | 人必須確認 |
|---|---|---|---|
| 成員 A：產品／領域與驗證 | 界定場景、訪談、主張與限制、組別敘事 | 整理回饋、產生比較材料 | 法律專業回饋真實性、事實與產品決策 |
| 成員 B：工程／資料與展示 | API、DB、UI、來源錯誤、展示環境 | 實作、測試、文件與差異分析 | 程式結果、資料條款與實際可重現性 |
| 共同責任 | 待辦排序、驗收、風險取捨、正式對外主張 | 多 Agent 分別提規格、實作與驗收意見 | 合併、發布、資料使用與效用結論 |

這是工作分配建議，不將未確認的既有成員身分寫成事實；兩人應能互相接替展示與故障處理。
AI 是執行與協作工具，不是法律覆核的替代品；獨立 Agent 審查仍可能有共同偏誤。

### 15.2 最小敏捷節奏

每一項待辦記問題、使用者證據、優先級、完成條件、負責人與狀態。
用「待確認→可做→進行→待驗收→完成」追蹤，未解阻礙明確列出，不把文件篇數當進度。
每輪只選少量能驗證的改變：一個回饋、一項修正、一個可觀察結果，再決定下一輪。
每日或每次工作結束留下簡短紀錄：輸入、做了什麼、驗證結果、未做、下一步。
每項改動獨立小提交；規格、實作與驗收分開角色檢查，對爭議保留決策理由。
既有送件稿描述看板、XP 實踐與 AI 結對；正式展示只談有原始紀錄支持的做法，不泛稱完整 Scrum 或嚴格 TDD。

## 16. 分期工作與驗收條件

以下是建議順序與範圍，不是已核定交期；每一期結束要有可檢視的產物。

| 期別 | 主要工作 | 完成產物與驗收門檻 |
|---|---|---|
| P0：版本與交接 | 固定分支、資料、展示與已知限制 | 新組員可從乾淨環境啟動；清楚說明重播與即時界線 |
| P1：真實回饋閉環 | 法律使用者觀看／操作、選一問題修正 | 回饋原文、排序理由、修正前後與重測；注明受訪身分與方法 |
| P2：商工可靠性 | 錯誤分類、限流／IP、欄位血緣、缺漏與分頁 | 六源契約、部分失敗測試、無假成功；新部署環境實測 |
| P3：事實包與新 run | 確認主體、案件日期、快照與事實契約 | 未確認／歷史不明資料不得靜默進推理；舊 run 保留 |
| P4：程序爭點小範圍推演 | 先做代表權、列法與管轄候選 | 同案新舊盲評，提示可回到來源與證據，不推個人責任 |
| P5：引用三層審核 | 命題、原文片段、適用性審核與正文對照 | 漏列正文引用可攔截；修訂後重審；時間版本明確 |
| P6：即時生成服務 | 工作任務、模型連接、成本、取消與重試 | 新案件可端到端；失敗不污染已完成紀錄；有費用上限 |
| P7：專業效用與檢索提升 | 強基準盲測、必要時向量檢索或異質模型 | 改善有證據；若無價值則縮減流程 |

### 16.1 開放資料整合的具體驗收案例

1. 名稱相似的兩家公司：未選定統編前不能自動進入分析；保留選定與確認紀錄。
2. 解散日期晚於契約日期：只提示目前程序問題，不寫成締約時無能力或契約當然無效。
3. 登記負責人與董事長不一致：不自動填代表人，輸出缺漏與需補文件。
4. 類型成功、董監事失敗：仍可顯示基本資料，但代表權未確認，不能偽裝完整查核。
5. 全部連線失敗：錄製資料有明確時間與來源，分析只能使用人確認過的快照。
6. 商號歷程多筆：保留原始各筆與日期，不能任意用第一筆假設當時狀態。
7. 分公司候選管轄：必須附業務關聯條件，不能把所有分公司法院都說成確定可起訴。
8. 公司資本額低：不得推導無資力、詐欺或負責人個人應清償。
9. 外國公司核准登記：不因不同於本國公司狀態文字就標成異常營業。
10. 舊分析＋新查核快照：UI 明示版本不同，重跑才產生新 run，不覆寫舊論證。

### 16.2 生成服務驗收前必備

建立可持久化執行狀態、每步模型與 prompt 版本、輸入／輸出追蹤、重試與取消。
做同一任務重送、模型中斷、外部查詢逾時、引用失敗、使用者取消與費用達上限的失敗路徑。
把「語意上應遵守」與「程式確實攔截」分別列在驗收表，避免文案寫得比實作強。

## 17. 決賽準備與組員交接

截至 10/27 已確認 LegalDebate 入圍 AI 工具運用組、商業治理 AI 創新組及鈦坦敏捷開發特別獎。
一般決賽規劃約六分鐘說明展示、七分鐘詢答，最終流程仍以官方行前通知為準；敏捷獎獨立場次不可自行套用相同長度。
官方 10/27 公告說明 11/2 下午寄分組與行前資料；目前不能把未公告的新 PPT 格式或期限當作確定規則。

| 對象 | 敘事重點 | 應準備證據 |
|---|---|---|
| AI 工具運用組 | 對抗協議如何增加爭點、減少錯用引用 | 同案前後、引用被攔截、流程與限制 |
| 商業治理 AI 創新組 | 商工公示資料如何落到程序準備 | 六源用途、統編查核、代表權／管轄卡、來源與失敗 |
| 鈦坦敏捷開發特別獎 | 如何從回饋改變待辦並驗證 | 日期、待辦、修正前後、回歸／CI、團隊交流 |

敏捷決賽評分為適應性 40%、可視性 30%、技術實踐 30%；重點是開發過程的真實證據。
本機初賽佐證已承諾決賽前收集法律系學生問卷或律師訪談，依回饋至少改一項；這一輪應優先完成。
看片概念回饋、實際操作回饋、執業律師效用評估分開寫，不能將學生滿意度說成律師驗證。
簡報可共用架構與案例，但各組調整重點；敏捷另準備過程與驗證頁，比直接重播功能介紹更貼題。
展示資料與截圖需遵守匿名規則，遮學校、指導老師與可識別資訊；公開資料也避免展示不必要的個人資訊。

### 17.1 每位組員應能獨立回答

- 系統的核心價值假設是什麼？與單次問模型的差異如何驗證？
- 三階段各做什麼？法官最終輸出為何不能稱勝率或法院裁判？
- 本次展示哪些是回放、哪些真正即時？離線失敗畫面會如何呈現？
- published 證明到哪一層？真實裁判為什麼也可能被錯用？
- 六種商工資料如何走入當事人卡？現在為什麼還不自動進攻防？
- 登記狀態與法律責任之間需要補哪些事實與覆核？
- 專案最重要尚未驗證的假設，以及下一項工作是什麼？

### 17.2 展示交接包

至少包含版本代號、啟動方式、案例順序、即時與錄製標記、網路測試紀錄、離線方案與已知問題。
另備本地簡報 PDF、短版操作錄影、原始來源連結與可重現測試結果；回放必須明示，不冒充現場生成。
正式案例與新實驗資料分開，避免演練時把 live 查核或草稿追加到不該更動的資料版本。
11/2 後再核對攤位、海報、設備、檔案繳交、敏捷場次、兩組時間與人力衝突，不憑前屆經驗定案。
