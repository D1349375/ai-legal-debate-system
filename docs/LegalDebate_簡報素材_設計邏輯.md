# LegalDebate 簡報素材：設計邏輯分部整理

> 依 2026-10-30 的程式（`ui-backend-integration` @ e85fbc1）、SKILL.md、五份 prompt 模板與 `docs/` 重新核對整理。
> 每一部分都分成：**做什麼／為什麼這樣設計／簡報可以講／被問到要誠實回答的限制**。
> 「簡報可以講」的數字都標了出處；沒有出處的不要上簡報。

---

## 0. 總主線（一句話與三段式）

**一句話**：LegalDebate 是台灣民事案件的「攻防預演與爭點整理」原型——原告、被告兩個 AI 角色先各自準備、再交互反駁，法官角色整理問題，最後留下**每條引用都查過來源**的爭點強弱評估與書狀骨架。

**三段式敘事**（所有組別共用）：

1. **問題**：法律 AI 有兩種典型失敗——編造聽起來對的法條／字號；單一回答只走一條看似合理的路，漏掉時效、備位、證據缺口。
2. **做法**：用「固定的對抗協議」逼出盲點，用「機械程式」守住引用與紀錄，不讓 LLM 自己查自己。
3. **證據與邊界**：跑過什麼、抓到什麼、哪些還沒驗證（尤其律師實際效用）。

**設計總原則（整份簡報的骨幹）**：**LLM 只負責判斷與論證；記帳、彙整、查證、閘門一律交給確定性程式，且 LLM 不能改。**
這句話可以解釋後面每一個設計選擇。

## 1. 要解決的問題與定位

**做什麼**：把「律師動筆之前」的準備工作前移——看見對方最強的理由、自己最薄弱的要件、還缺哪份證據。

**為什麼這樣設計**
- 單一模型直接整理案情，容易選定一條路就走到底；雙方先獨立準備再強制回應，可觀察主張是否因反駁而修正。
- 要求每一方在 Stage 2／3 提出 **falsifier（讓步條件）**：把「我很有信心」改成「若哪項事實被證明，我必須改變結論」，產出可稽核的弱點。
- 輸出定位是**爭點強弱評估**，不是判決預測。程式命名沿用 `verdict`，但對外一律說「爭點強弱評估」，prompt 明文禁止「本院判決」「應予維持」這類措辭。

**簡報可以講**：產品目的是「幫律師決定哪些爭點該優先寫進訴狀、力度多強」，不是預測勝率。

**誠實限制**
- 「對抗協議比單一 Agent＋檢索＋批判查核更有用」目前只是**待驗證假設**（規劃書 §1、§12.3），沒有對照實驗。
- 法律定位：律師法第 127 條，不能做面向一般民眾的收費代撰；定位是律所內部輔助工具（README）。

## 2. 整體架構：三層分工

| 層 | 誰負責 | 內容 | 能不能被 LLM 改 |
|---|---|---|---|
| **角色層** | LLM subagent | 原告律師、被告律師、法官的論證與訊問 | 這是 LLM 的工作 |
| **調度層** | 主 agent（Claude Code） | 照 runbook 依序派工、整理摘要、呼叫 CLI 落地 | **禁止自己判斷案件實質**、不得加開輪次、不得自己改引用 |
| **確定性層** | Python（`engine/`、`database/`） | 機械彙整、引用查證、商工規則、落地閘門 | LLM 完全碰不到 |

**十步流程**（SKILL.md）：案件輸入 → 商工查核與起訴審查 → Stage 1 → 法官訊問 → Stage 2 → Stage 3 → 機械彙整 → 法官評估 → 引用查證 → 書狀骨架 → 回報。

**為什麼這樣設計**：主 agent 被限定為「流程調度員／記帳員」，就是為了避免出現第三個隱形的律師或法官；每個決策點都有一個「誰有權、誰無權」的明確答案。

**簡報可以講**：一張三層分工圖就能說明為什麼這不是「叫模型演三個角色」。

## 3. 對抗協議：Stage 1 → 訊問 → Stage 2 → Stage 3

### 3.1 每一階段的目的

| 階段 | 目的 | 關鍵設計 |
|---|---|---|
| **Stage 1 爭點整理** | 雙方獨立盲判，保留不同出發點 | 看不到對造輸出；「請求權基礎檢驗法」四步：窮舉候選→逐項要件涵攝→預想反駁與備位→整合立場 |
| **法官訊問** | 逼雙方把已提出的主張講扎實 | 每則訊問必填 `based_on`，回溯到 Stage 1 具體哪句；不得憑空開新爭點；沒有真爭點可以回空陣列 |
| **Stage 2 訊問攻防** | 面對反駁 | 只給對造的**結構化摘要**（立場＋最強論點＋引用），不給全文；必須提 falsifier |
| **Stage 3 辯論終結** | 收斂，不再開新方向 | 盤點兩輪候選→標記「仍站得住／已被打掉／未經檢驗」→決定最終立場；必須正面回應對方**最強**論點 |

### 3.2 為什麼這樣設計（簡報重點）

- **盲判（Stage 1）**：避免一開始就互相模仿，保留獨立的候選路徑。
- **只給對造摘要不給全文（Stage 2／3）**：這是針對「多 Agent 同質化」的刻意對策——阻擋修辭趨同，逼雙方正面對決論點本身。
- **請求權基礎檢驗法**：模仿德國式請求權檢驗，窮舉候選、逐要件標記該當／不該當／資訊不足。目的是防止「只挑最直接的一條就停」。
- **內部一致性檢查（Stage 2／3）**：防止同一方在不同輪次自相矛盾（例如一邊主張契約已完全履行、一邊又主張時效從完工日起算）。這是**實測中真實出現過的錯誤**，才加進 prompt。
- **對造引用判例查核鐵律**：對方引了判例，必須先 Read 該判例全文，確認案由與爭點是否真的支持其主張，才能回應。
- **固定三輪、禁止加開**：成本可控、可比較；不因「感覺可以再辯一輪」而擴張。
- **五準則**（不重複、開新視角、直接回應、帶新依據、改變表達）：對抗同質化與灌水。
- **Prompt 版本有 A/B 依據**：請求權基礎檢驗法版取代舊版，是經 5 案 A/B 測試後才定案（`docs/en/prompt-comparison-claim-basis-batch1/2.md`），其中一案有污染揭露。

### 3.3 誠實限制（Q&A 準備）

- **單一模型、多角色**：隔離只在「編排層紀律」（上下文分開、輸入資料不同），**不是**工具權限或資料權限的完整隔離。同質化風險存在，規劃書把「異質模型矩陣」放在 Phase 3，由實測證據觸發。
- **雙方讀的是同一份事實，沒有「我方／對造各自掌握的資料」**：案件輸入只有一份 `facts_summary`＋`claims`，程式裡沒有「使用者代理哪一方」的欄位，原被告 subagent 讀同一個檔案。所以對造模擬的是「同一份事實下，另一位法律推理者會怎麼攻」，**不是對造實際握有的事實**。真正的資訊不對稱（各自握有不同證據）屬規劃書 Phase 3 的設計，尚未實作。
- 溫度無法透過 Claude Code 派工機制設定，已明列為已知限制，**沒有假裝在 prompt 裡寫「請用溫度 0.2」**。
- 立場驅動檢索（`stance_rag.py`）只是**關鍵字組字串**，不是向量語意檢索；檢索不到時靠 subagent 自己的法律知識，之後交由查證層把關。

## 4. 法官角色與「機械錨點」

**做什麼**：法官有兩次出場——Stage 2 之前（爭點確認＋訊問）、Stage 3 之後（爭點強弱評估）。

**為什麼這樣設計**
- 法官的判斷範圍被縮到「哪些是爭點、該問什麼」，**不得在訊問階段透露對案件實質的傾向**。
- 最終評估受**機械錨點**約束：`engine/aggregate.py` 先算出 `weak_points`（誰在哪個爭點有明確 falsifier）與 `position_drift`，法官的敘述**只能在此方向內補充，不得推翻**；若直覺與錨點衝突，要在文中誠實說明疑慮而非悄悄改口徑。
- 評估必須輸出 `risk_map`：對原告不利、對被告不利、建議補強證據——直接對應律師的下一步行動。

**簡報可以講**：「LLM 法官不能自己決定誰比較弱，弱點是由雙方自己交出的讓步條件機械彙整出來的。」

**誠實限制**（一定要主動講，否則被問倒）
- `weak_points` 只是把雙方 Stage 3 的 falsifier 收集排序，**不理解法律要件，不是勝負機率**。
- `position_drift` 是「Stage 1 → Stage 3 引用集合的 Jaccard 距離」，只是引用變動的代理指標；只改文字不改引用會是 0，加不相關引用也會升高，**不能當品質指標或排行榜目標**。

## 5. 引用查證：三層分開、機械閘門

這是最能對應「減少錯用引用」的一塊。

### 5.1 三層（不要混在一起說）

| 層次 | 問題 | 誰做 | 現況 |
|---|---|---|---|
| ① 來源存在與身分 | 這條法條／字號真的存在嗎？ | `engine/verify.py`（程式） | 已實作 |
| ② 內容支持 | 原文真的支持這個命題嗎？ | 獨立乾淨 context 的 subagent 讀原文（Step 8 第二項任務） | runbook 要求＋案例紀錄；尚無完整結構化資料模型 |
| ③ 個案適用 | 本案事實、時間版本、證據相符嗎？ | 律師覆核 | 系統不保證 |

### 5.2 ①的運作

- **法規**：每次都回頭查全國法規資料庫（`law.moj.gov.tw`）官方條文，不信快取。支援民法、公司法、勞基法、消保法、刑法、民事訴訟法、企業併購法。
- **判決**：先比對本地語料（最高法院民事 1,088 筆，來自司法院開放資料），未命中就**即時查 FJUD**，並精確比對年度／字別／字號，避免採到相近案號。回傳區分 `published`／`not_found`／`verification_failed`（連線失敗≠查無）。
- **本地語料庫只是加速層，不是權威**。

### 5.3 機械閘門

- `record_verdict`、`record_pleading` 遇到任何未 `published` 的引用就**直接 raise 拒絕落地**；runbook 明寫這「不是你的判斷空間」。
- 同一角色同一階段、案件、評估都**不可覆寫**；書狀可追加版本（律師編輯版另存一列，原稿不動，引用逐條重驗，未通過不得匯出）。
- 查證 subagent 必須是**新的乾淨 context**，不能由寫論證的同一個 context 自己查自己。

### 5.4 實測抓到的案例（可上簡報，出處：`docs/en/e2e-test-report-2026-08-09.md`）

- 一筆「最高法院 105 台簡上 33」：**被告 Stage 2 在本地語料找不到 → 保留異議；FJUD 即時查證 `not_found`；原告 Stage 3 自行撤回該引用**。三個獨立機制得到同一結論（LLM 自查、對造交叉檢驗、機械查證）。
- 真實存在但**案由無關**的判決（115 台簡上 8 講本票舉證責任，與清償抵充順序無關）被被告識破——證明「存在」與「支持命題」必須分層。
- 查證引擎自己的 bug 也被抓出並修正：「民法第 191 條之 2」曾被解析成第 191 條（**查到錯條仍通過，比查不到更危險**）；字別白名單漏掉「台簡上」。兩者都補了回歸測試。

### 5.5 誠實限制

- `published` 只證明到「存在且身分相符」；**不代表內容正確、不代表適用於本案**。
- DB 閘門只檢查呼叫端傳入的 `citations_used`；呼叫端若漏列引用，空清單也會通過（規劃書 §6.4 自己列為缺口）。
- 範圍有限：只涵蓋七部法律與最高法院裁判；其他法院、歷史版本未全面涵蓋；項款適用沒有逐項核對。

## 6. 官方事實層：商工登記 → 起訴審查

這一塊是**商業治理 AI 創新組**的主軸，也是 10/28 之後新增最多的部分。

### 6.1 做什麼

- 串接經濟部商工開放資料 **6 個資料集**（統編類型、公司基本資料、董監事、分公司、關鍵字、商業登記），依**使用者提供的統編**查核當事人。
- `engine/party_rules.py` 以固定規則把登記狀態轉成警示（約 19 種警示代碼：解散、清算完結、重整、臨時管理人、合併、破產、分公司、名稱不符、停業……）。
- `engine/party_issues.py` 再把警示轉成**起訴審查時審判長應命補正的程序事項**（法定代理、當事人能力、當事人適格、當事人表明），附民訴法依據。
- 這些事項在 **Stage 1 之前**交給雙方：原告要在 Stage 1 寫「程序補正(<id>)」段落；法官只就補正不足者追問；最終評估要「先交代程序事項，再談實體」。

### 6.2 為什麼這樣設計

- **確定性規則，不讓模型補造公示事實**：規則可稽核、可測試；「不是 LLM 產出，主 agent 也不得自行增刪」。
- **統編只能來自使用者**：同名公司很多，用名稱搜尋後自行選定就是查錯人。
- **未查核不等於沒有程序問題**：`notes` 會記錄哪一方未查核或查核失敗，回報時照實說。
- **對齊實務流程**：實務上法院收狀先審查當事人能力與法定代理權，可補正者命補正，逾期以裁定駁回（民訴 §249 Ⅰ）。
- **設計上的細膩處（很適合 Q&A 展現深度）**：最高法院 115 台抗 105 號——一審憑登記駁回、後經廢棄確定，因為法院須**依職權調查實際代表權，不得僅憑登記**。所以系統**只提出「命補正事項」，不替法院下「應駁回」的結論**；`main.py verdict` 還會機械拒絕把 §249 與該裁定放在同一個括號裡的評估（避免讀起來像該裁定也支持駁回）。
- **登記資料是「查詢當下」狀態**，不一定等於案件事實發生時的狀態；兩者可能衝突時照實指出。

### 6.3 簡報可以講

「公示登記資料如何變成程序準備」：被告已解散 → 法定代理人應列清算人而非原負責人 → 原告須補正 → 法官追問 → 評估把它列為風險並列出該調閱的資料（解散前變更登記表、清算人就任聲報）。有一個實際案例：`test-2026-10-27-gcis-001`（取材最高法院 114 台上 1987 裁定，當事人匿名化）。

### 6.4 誠實限制

- 規則由人撰寫，涵蓋範圍有限；分公司本功能不查登記資料。
- 錄製的查詢結果會標示「⏺ 錄製」，不得冒充本次即時查詢。
- 外部網站欄位可能變更，歷史連線成功不等於長期可用。

## 7. 書狀骨架（起訴狀＋答辯狀）

**做什麼**：Step 9 依一方的 Stage 3 輸出，產出**民事起訴狀骨架**（9A）與**民事答辯狀骨架**（9B）；9C 可只替既有案件補產缺的那份，不重跑攻防。使用者可選要產哪幾份，以控制花費。

**為什麼這樣設計（刻意的保守）**
- **骨架版，不潤飾**：直接套 Stage 3 的 position／argument／引用，不做語氣改寫。語氣蒸餾要等 Phase 2 取得律師語料，現在誠實說「這是骨架」。
- **只用 `published` 引用**，閘門再擋一次。
- **案號、股別、法院、證物、日期一律「(待填:…)」**，不得編造。
- 當事人欄照商工登記填，法定代理人只填查核結果有帶入的人；被告已解散時寫「清算人(待查明:…)」，**不得照列原負責人、不得編造清算人姓名**。
- 答辯狀欄位依民訴 §116、§266 整理，並**如實說明不是來自官方答辯狀範本**（本機只有起訴狀範本）。
- 被告 Stage 3 沒表示意見的點，寫「待律師補充」，**不得代被告表態**。

**誠實限制**：非可直接送件成品；真實訴狀語料（Phase 0）至今仍未取得，是**取得性問題**而非工程問題。

## 8. UI 與即時執行：展示的真實性

**做什麼**：UI 七個分頁（總覽、當事人、攻防、機械彙整、引用查證、爭點評估、訴狀）；可從 UI 建立新案件、按「即時執行」在本機啟動 Claude Code 跑完整 legal-debate skill。

**為什麼這樣設計**
- **逐筆標示來源**：「⚡ 本次即時生成・執行 #N」vs「⏺ 錄製紀錄」，不讓錄製冒充即時。
- **權限收窄**：`--permission-mode dontAsk`，只允許 `python main.py *`、legal-debate skill、Read／Grep／Glob／Agent；寫檔只限 `database/live_runs/`；shell 迴圈與導向到其他路徑一律被拒（有以假 API 驅動真 Claude Code 的測試，不耗額度）。
- **可續跑、可取消**：落地紀錄不可覆寫，所以中斷的案件從「第一個尚未落地的階段」續跑；取消會終止整個程序樹，已落地階段保留。
- **花費上限**與 token／額度記錄；**書狀由使用者選**（只產起訴狀／只產答辯狀／兩份），沒有預選。
- **安全分類器中止（`reasoning_extraction`）**：實跑中真的發生過，SKILL.md 規定用同一份範本重派新 subagent、最多 2 次，**不得精簡範本去迴避**，每次中止都要在回報中列出——這是「如實呈現失敗」的好例子。

**簡報可以講的實測數字**（出處：`ui/README.md`）：一件約 11–15 分鐘、Claude Code 估算約 2.5–3.3 美元（Pro 訂閱帳號，2026-10-28／29 執行 #2、#4）。

### 10.3 Q&A 預備（每位組員應能獨立回答，規劃書 §17.1）

1. **核心價值假設是什麼？怎麼驗證？** 對抗協議＋查核紀律比單次問模型更容易暴露盲點；驗證方式是 §12.3 的三組對照（尚未做）。
2. **為什麼不叫判決、不給勝率？** 目的是決定訴狀優先順序；錨點只是 falsifier 彙整，不是機率。
3. **哪些是回放、哪些即時？** UI 逐筆標示；離線時本地快取會標 `local_cache_only` 並阻擋。
4. **`published` 證明到哪一層？** 只到存在與身分；內容支持靠獨立 subagent；個案適用靠律師。
5. **單一模型扮演三角色，會不會自己跟自己吵？** 會有風險；目前靠上下文隔離、對造只給摘要、falsifier 與機械彙整對抗；異質模型矩陣待實測證據再決定。
6. **為什麼書狀不潤飾？** 沒有律師語料就不假裝有文風；骨架誠實標示。
8. **律師只會代理一方，只輸入一方的資料，怎麼模擬雙方攻防？** 如實回答：兩個角色讀同一份事實，被告方（或對造）沒有自己的私有事實，只能就這份事實找抗辯路徑（要件不該當、時效、備位、證據缺口）並反駁；它是對己方論證的**壓力測試**，不是預測對方實際握有什麼。輸出的「建議補強證據」就是在指出對造最可能攻的缺口。真正的資訊不對稱列為後續階段。
7. **為什麼不直接上傳 PDF／圖片？** 增加的是輸入便利，不增加分析品質，且抽取錯誤會污染整場辯論；證物導入是另一個需要重新設計證據模型的大功能。
