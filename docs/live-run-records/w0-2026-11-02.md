### V35 的兩處邊界

- 訊問 3(問原告):「你方 Stage 1 自陳這一點「證據不明,需查證」」。原句確實在原告 Stage 1 公開論證,轉述正確,所以判成立。但這是原告的資料缺口標記,依 M12 的設計應該被擋;`engine/admission_check.py` 的 `_SOFT_RE` 沒有「證據不明」「需查證」,所以 `check-judge` 放行。
- 原告 Stage 3:被告「自承「被告若主張更早知悉,則由被告就更早知悉負反證責任。」」。原句在被告 Stage 2 公開論證,是被告對舉證責任的法律見解,原告只拿來說明舉證責任,沒有轉成事實承認,所以判成立。`record` 因原句是條件句發出警告。若採「條件句一律不得稱自承」的嚴格標準,這處不成立。

## 其他發現

1. **主 agent 改了機械彙整**:落地評估時,`mechanical_anchor_json` 的 `weak_points[].response_excerpt` 被換成「(…摘錄從略…)」,`procedural_issues` 也少了 `warning`、`question_text`、`procedure`。主 agent 在最後回報自己寫明了這件事。SKILL 禁止修改機械彙整結果;`anchor_check` 只比對 `position_drift`,所以仍顯示一致。
2. **法官轉述了錯誤條文**:訊問 2 照被告說法寫「公司法第23條第3項(公司對負責人訴訟之代表人)」,但該項是歸入權規定。原告在 Stage 2 指出,評估也記下這點。
3. **CLI 在 Windows 會先用 PowerShell 工具**:被拒 2 次。第一個查證 subagent 因此沒跑 `verify`,主 agent 另派一個改用 Bash 才完成。
4. **對手摘要的「最強論點」選句**:被告 Stage 2 被選出的句子是「被告若主張更早知悉,則由被告就更早知悉負反證責任。」,這是舉證責任的讓步句,不是被告最強的論點。原告隨後把它寫成「自承」。M14 只要求逐字,沒有規定怎麼選。
5. 內建瀏覽器會自動取消 `window.confirm`,所以按「開始即時執行」時,先在頁面上讓該次確認回傳同意。這只是測試環境的操作,不影響產品。
