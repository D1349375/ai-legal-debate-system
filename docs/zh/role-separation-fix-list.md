## A. 已重現的錯誤

以下每項都用 `85b8bbe` 的程式實際跑過。

### A1. 查不到不在本機語料的判決全文

- **位置**:`engine/verify.py:250` `_fetch_judgment_text`
- **重現**:對 `TPSV,105,台簡上,33,20161026`、`TPSV,111,台上,1,20220120,1` 實際連線,案由抓得到,但 `full_text` 長度是 0、`doc_type` 是 `None`。
- **原因(推測)**:全文容器的正則用非貪婪比對到第一個 `</div>`,實作時請對照實際 HTML 確認。
- **影響**:`verify_precedent_note` 會回 `doc_type_mismatch`。語料只有最高法院 1,088 筆,所以語料外的判決全部無法正式引用。
- **修法**:
  1. 修全文解析,必須取得正文而不是空字串。存一份官方頁面 HTML 當離線測試資料。
  2. 頁面解析失敗要回獨立狀態,例如 `full_text_unavailable`,不要回 `doc_type_mismatch` 或 `quote_not_found`,那會讓人以為引用寫錯。
- **驗收**:V1

### A2. 官方事項 id 被當成主張編號拒絕(打到商業組主軸)

- **重現**:

  - 評估寫 `程序補正(plaintiff:dissolved)尚未完成。` → `item 參照格式錯誤`
- **影響**:`judge_question_prompt.txt:11` 要求「說明並列官方事項id」,照做就會被拒。商工解散案是商業組示範主軸。

## B. 走過頭的方向,請放寬

### B1. 不要由程式打高中低

**問題**:這和舊版「機械錨點」是同一種錯。輸入仍是 AI 自己標的狀態,程式算成等級,法官要寫理由才能偏離。

`reference_grade` 實際輸出:

| 情境 | 結果 |
|---|---|
| 書證齊全,一個要件靠合理推論(例如過失),對方未主張 | 低 |
| 主位要件全有事實,備位被對方打掉 | 低 |
| 要件全有書證,對方只提一個沒有事實的法律抗辯 | 中 |
| AI 自標「已成立」並引一個事實編號 | 高 |

過失、因果關係多半要靠推論,這樣打分會系統性偏低。

**改法**:拿掉 `reference_grade` 與 `grade_reason` 的強制關係。等級由法官寫,程式只檢查 `basis`、`own_items` 等依據確實存在,畫面並列原文。

### B2. 文字規則不要誤擋正常句子

實際被拒絕的句子:

| 句子 | 被拒原因 |
|---|---|
| 原告尚缺佐證文件,應請當事人補提。 | 「佐證」要同句兩個事實編號 |
| 原告並未自承任何事實。 | 否定句也算「自承」 |
| 被告主張已清償,見存證信函,惟未提出單據。(起訴狀) | 禁詞「被告主張」 |

**改法**:

- `engine/role_protocol.py:467` 只查「相互印證」「互相印證」,不查「佐證」。
- `ADMISSIONS` 保留硬擋,這是核心錯誤鏈,但要排除否定句。
- `database/db.py:319` 起訴狀字樣改成警告並在畫面顯示,不拒絕落地。流程用語(Stage、輪次)可以考慮維持硬擋。

原則:**結構規則可以硬擋**(編號存在、狀態轉移、撤回依據);**自然語言規則預設只警告**。模型被反覆退回的成本比一個警告高很多,而且現場會中斷流程。

### B3. 不要每一筆待確認都要法官回應

**問題**:`validate_verdict`(:484)要求 `pending` 逐筆回應。002 第一輪原告 22 項有 16 項待確認,被告 25 項有 23 項,加上要件還會更多。

風險是從「亂下結論」變成「什麼都不下」:法官寫一大串「待確認」,律師拿到讀不完的清單。這點要等 002 最終數字才能確定。

**改法**:

- 官方程序事項與 `defeat_conditions` 維持逐筆回應。
- 待確認改成**依爭點或持有人彙整回應**,只檢查每個爭點有處理。
- 待確認清單要有排序,先列影響主要請求的項目。

### B4. 每輪落地不要因連線或全文問題拒收

**問題**:`validate_argument` 會呼叫 `validate_precedent_notes`,落地時就連網查判決。A1 沒修時語料外判決一律失敗;現場網路不穩時,也會讓某一輪落地失敗。

**改法**:語料內維持文件身分與摘句檢查。語料外或連線失敗時,標「律師待核」,主張照常落地,書狀閘門才擋。

### B5. 恢復書狀選擇,說清楚適用範圍

**問題**:

- `database/db.py:316` 擋掉非代理方的書狀。`main` 已有的「只產起訴狀/只產答辯狀/兩份都產」被改掉。
- `role_protocol.py:340` 一律是「起訴前」,但被告律師受任時通常已經有起訴狀。

**改法**:

- 代理方的正式書狀與對方預演要點,讓使用者選要產哪些,保留控制花費的設計。「非書狀」的標示要留著。
- 決賽前不用做「已收到起訴狀」的新流程,但畫面要寫清楚:目前的被告草稿是預先準備,不是回應實際起訴狀。
