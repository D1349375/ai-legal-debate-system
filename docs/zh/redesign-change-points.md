# 改動點（給組員）

> 2026-10-31 起逐項討論，討論完一項就更新一項。實作細節（改哪些檔、怎麼測）在 [修改實作計畫](role-separation-redesign-plan.md)。
> 分支：`role-separation-redesign`。

## 為什麼要改

我們檢查了三件測試案件的完整紀錄，加上用真實判決、換成 Codex 模型重跑的兩案，結論是：**大部分錯誤不是模型亂講，而是流程把模型推向錯誤。**

最典型的一條鏈（002 追撞案）：

1. 案件事實只有原告的說法，被告 agent 沒有自己的事實。
2. 法官問被告「有沒有行車紀錄器」，被告只能答「資料沒寫，要查證」。
3. 這句話一路被改寫：「資料沒提到」→「現無行車紀錄器」→ 原告寫「被告已自認沒有證據」→ 寫進起訴狀。

換成 Codex 模型、用真實案件跑，「自認」沒有出現，但被告把「時效」抗辯撤掉了，理由是「日期資料不足」，而真實法院正是靠時效駁回原告。兩個模型都會把「缺資訊」變成某種立場，所以是流程問題，不是單一模型的問題。

根因有兩個：

- **流程寫在文字說明裡，由 AI 照著演。** 調度、摘要、規則遵守都靠主 agent 讀說明自己決定，所以每次跑都不太一樣，紀錄也無法重現。
- **系統沒有「缺資訊」的位置。** 使用者只代理一方，對方 agent 本來就不會有對方當事人的事實；但流程把它當成知道內情的律師，逼它回答事實、寫讓步條件。

## 改動的大方向

1. **案件記錄「使用者代理哪一方」。** 代理方是真的律師；另一方改成「預測對方律師可能怎麼打」，不再假裝知道內情。
2. **新增「待當事人確認」狀態。** 資料沒寫的事就是待確認，不能變成承認，也不能變成撤回。
3. **規則從文字說明搬進程式檢查。** 違反規則的輸出由程式擋下，不靠 AI 自律。

## 各步驟改動

### 1. 案件輸入 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 新增「代理方」欄位（原告或被告），建案必選 | 後面所有角色規則都依它決定 |
| 案件事實分三欄：預期雙方不爭執的／原告方的說法／被告方的說法 | 原本只有一欄，被告不知道自己讀的是原告版本 |
| 每則事實可標「〔書證：名稱〕」 | 被告能分辨哪些是 email、筆錄這種書證，哪些只是單方說法。001 被告就是拿原告自己的 email 建構出「瑕疵通知」的論點 |
| 代理原告時，被告方那欄寫的是「原告轉述或書證所載的對方說法」 | 不能把它當成被告自己的陳述 |
| 只支援「起訴前」情境 | 產品定位就是律師動筆前；聲明裡出現「原起訴」「變更聲明」會警示 |
| 新增請求金額欄位，依金額提示小額／簡易／通常程序 | 002 請求 18.5 萬，本該走簡易程序，系統卻照一般程序跑。只警示不阻擋 |
| AI 角色讀的案件檔由程式產生，不含案件來源（真實法院與字號） | 原本角色看得到來源字號，會洩漏起訴年度等資訊 |
| UI 建案表單同步改：代理方、三欄事實、金額 | 排在時程第三層，簡報先用示意圖 |

### 2. Stage 1 爭點整理 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 每個主張或抗辯變成一筆有編號的項目，標明要件、狀態 | 後面的階段靠編號追溯，不再靠 AI 重讀重摘，「如果」「資料沒寫」這類限定語就不會在轉述中掉 |
| 自我弱點移到「內部備註」，法官和對方看不到；代理方的備註會給使用者 | 原本自我檢討和論證寫在同一段給法官看，被法官寫成「被告已自承」（001、002、003 都有） |
| 代理方：資訊不足的要件列成「要請當事人補的資料」 | 直接變成律師的待辦 |
| 對方（預測對方律師）：產出三類——用我方事實打、指出我方證據缺口、需要對方事實的假設抗辯（一律待確認） | 對方仍有自己的論點，只是沒有自己的事實；例如 002 用警詢那句「我以為前車要起步」主張原告也有過失 |
| 三輪都加規則：資料沒寫的事寫「待確認」，不能寫成有或沒有 | 002：「資料沒提到行車紀錄器」被寫成「現無行車紀錄器」 |
| 要件寫「已成立」時，要指出是哪一則事實；沒有就是推論 | 把事實和推論分開，避免推論跳太遠 |
| 引用判決前必須讀過全文並寫一句「這個案子在處理什麼」；憑記憶想到的只能當檢索線索 | 002 引用的判決是醫療糾紛、職災、國賠，跟車禍無關 |
| 立場限一兩句；立場依據的項目若還是待確認，程式擋下 | 問題不是寫太多，而是混在一起、壓得太兇；用結構解決，不用字數 |

### 3. 法官訊問 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 法官看不到內部備註 | 自我檢討不會再被寫成「承認」 |
| 每題要指到具體的主張編號，程式檢查編號存在 | 原本法官要回溯 Stage 1 的「某一句」，條件句因此被標成「自承」 |
| 一方沒提到的事不算「不爭執」；第一輪雙方看不到彼此，不能寫「未回應」 | 003：第一輪雙方互相看不到，法官卻寫「被告沒有回應」 |
| 出現「自承／自認／坦承」，程式檢查指到的是不是對方真的主張過的事實 | 擋住 002、003 那種從「待查證」變成「承認」的鏈 |
| 每題標「法律題」或「事實題」；對方 agent 只能收到法律題 | 對方 agent 沒有對方的事實，問事實題只會得到「待查證」，又被扭曲成「承認沒有」。法律題（例如「這封 email 算不算通知」）它靠我方的事實就能回答，而且逼出來的正是我方要準備的攻防 |
| 我方 agent 可以收到事實題，答「待確認」時程式不准改寫成「沒有」 | 我方背後有真人，這種題目等於告訴律師「法院一定會問，先去問當事人」；同時列進「請當事人補的資料」 |
| 原本想問對方的事實題，由法官改寫成給我方的「準備清單」：對方可能拿出什麼、會打到我方哪個主張、要先準備什麼 | 例：「對方可能有行車紀錄器 → 影響『我方完全停等』→ 先確認車輛是否靜止、調閱路口監視器」 |
| 準備清單每筆都標成假設，不傳給對方 agent、不進起訴狀 | 避免「對方可能有」又變成「對方已經有」 |
| 我方在第二輪逐筆想好應對，寫進內部備註，不寫進論證 | 律師開庭前先演練一輪；但寫進論證會被法官和對方看到，也可能被當成「原告承認對方有影片」 |

### 4–5. Stage 2、Stage 3 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 給對手的摘要改由程式產生，固定格式，含「尚未確認的事實」欄位 | 原本由主 agent 自己寫，「如果」「資料沒寫」被濾掉。002：原告拿到「現無行車紀錄器」，就寫成「被告已自認沒有證據」 |
| 法官說錯我方主張時，可以用編號更正 | 原本規定「法官說是你的主張，你就必須認」，誤會無法更正 |
| 代理人不得未經當事人同意承認事實、接受金額 | 002：被告寫「如果查不到影像就賠」，被當成認輸 |
| 「讓步條件」改問「什麼證據會改變我的看法」，兩邊分開處理：我方寫的放內部備註，只給使用者看；對方 agent 寫成「若原告拿出 X，這個抗辯就失效」，可以公開 | 我方寫的本質是自我弱點，給法官看到又會變成「承認」；對方寫的正好告訴原告要準備什麼 |
| 待確認的項目只能附依據撤回：資料直接證明不成立（寫事實編號），或被對方的法律論點打掉（寫對方編號）。「資料不足」永遠不是理由 | Codex 那輪被告以「日期資料不足」撤掉時效抗辯，而真實法院正是靠時效判原告輸。同一輪也以「沒有本人事實」撤掉「善意受領、利益已不存在」（民法第182條），真實被告正好提了這項抗辯 |
| 「策略性撤回」只有我方可以，對方 agent 不行 | 我方背後有真人可以做決定；對方 agent 是模擬的，真正的對方律師會保留所有站得住的抗辯 |
| 項目不能在後面的輪次消失，只能改狀態 | 避免抗辯不聲不響地不見 |
| 最後一輪的收斂只針對已主張的項目；待確認的一路保留，最後列成「待當事人確認清單」 | 原本「收斂」「不要誇大」的要求讓對方 agent 把沒證據的抗辯全部收掉 |
| 發言規則從五條改成三條：不重複、開新的法律角度（不能補新事實）、直接回應 | 「每輪帶新依據」逼模型湊判決，002 那幾個類型不對的判決很可能這樣來；「換一種說法」讓限定語在改寫時掉，「資料沒提到」變成「現無」就是這樣 |
| 最後一輪分成「我方主張本身」和「對對方的反駁」兩欄 | 起訴狀只能用前者（第 9 項） |

### 6. 機械彙整 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 拿掉「弱點」欄位 | 原本程式把讓步條件（「如果…就…」的假設句）原封不動抄成弱點，法官又不准推翻，等於被逼著把假設當結論。003：法官寫「被告承認最大證據缺口，與彙整結果相符」，其實是同一句話抄過去，自己證明自己 |
| 改整理成「原告要準備的證據」：對方 agent 寫的「若原告拿出 X，這個抗辯就失效」，每筆對到對方的主張編號 | 告訴原告拿出什麼能打掉對方的抗辯；不叫任何一方的弱點 |
| 待確認清單依「東西在誰手上」分三種：問我方當事人、對方可能有、需向第三方或法院調閱 | 三種的做法不同：去問、先想好應對、聲請調查證據。002 的路口監視器、警方事故分析就屬第三種 |
| 「立場位移」改名「引用清單差異」，先統一引用寫法再算；畫面、回報一起改名；不交給法官 | 它算的只是引用清單差多少，002 法官看到數字高就寫「攻防拉鋸」 |
| 新增「主張狀態變化」：哪些主張從主張變撤回、從待確認變成立，每筆附原因；只給使用者看 | 這才是真正的立場變化，而且查得到原因 |
| 法官對彙整結果改成「每一筆都要回應，但不規定方向」；提到待確認的項目必須照寫「待確認」 | 保留「AI 法官不能自己略過重點」，又不被逼著同意假設；程式只能檢查有沒有提到，所以另外守住「待確認」字眼不能弄丟 |

### 7. 法官評估 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 法官引用任何一方，都要附編號和輪次，例如 `D3@S3`（被告第 3 項、第三輪）；程式檢查真的存在 | 001：法官說被告原本主張「全額不付」，但被告從頭到尾只主張扣掉短少零件的部分 |
| 說立場改變時並排兩個輪次，程式對照「主張狀態變化」，紀錄說沒變就擋下 | 防止法官自己編出立場轉變 |
| 畫面上自動帶出法官引用的那一項原文 | 程式只能查編號存在，查不出描述對不對；讓使用者一眼比對 |
| 寫「互相印證」時必須列兩個不同的案件事實編號（F 開頭），不接受主張編號 | 雙方主張可能都源自同一則事實；003 法官拿同一句話自己證明自己 |
| 評估改成逐爭點表格：我方主張、對方主張、強弱、依據（事實編號或標明推論）、還要補什麼；最後只留幾句結論說明書狀先寫哪些爭點 | 每個判斷都查得到依據，律師讀表格也快 |
| 「高／中／低」依主張狀態定義，程式先算參考等級；法官可以給不同等級，但要寫理由 | 不然只是換個方式憑感覺打分 |
| 提到待確認的項目必須照寫「待確認」 | 守住「待確認」字眼一路不弄丟 |

### 8. 引用查證 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 同一字號有多份文件時，要指定裁判日期，否則不准標「已查證」 | 原本程式取資料夾裡第一個檔案。114 台上 1945 有程序裁定和實體判決兩份，會取到程序裁定 |
| 法規白名單補上實際出現過的法律（銀行法、民法債編施行法等）；不支援的標「不支援」，和「查無」分開 | 原本只有 8 部法律，引用其他法律必定查證失敗，Codex 兩案都卡在這裡 |
| 查證紀錄改成每案、每次各一筆 | 原本是全域共用，無法知道是哪一案、哪一次驗過的 |
| 判例內容比對分三層：① 案由與判決／裁定類型，程式比對 ② 引用附的原文摘句必須真的出現在全文，程式比對 ③ 是否真的支持論點，由獨立查證 agent 判斷 | 原本只查「字號存在」，002 那幾則醫療糾紛、職災、國賠判決全部通過查證 |
| 案由不同不自動擋下，標「需說明」並要求寫出類推理由 | 有些不同案由的引用是合理的類推，例如用商譽損害判決說明法院酌定損害金額的標準 |
| ①② 涵蓋三輪辯論與評估中的所有判例引用；③ 只做最後採用的 | 第二、三輪新增的引用會進到給對方的摘要；第三層成本高，所以限縮 |
| 引用查證改用固定範本，輸出結構化結果 | 原本只有一段說明文字，Codex 兩案都在這一步失敗 |
| 引用舊版條文時標「版本未查證」，不准標「已查證」 | 002 引用 108 年版民法第205條（年息上限 20%），程式查到現行條文（16%）就標已查證，等於驗錯版本也算過 |
| 「版本未查證」「不支援」的條文不擋評估，但不能進書狀，回報列為「律師待核」 | 舊版條文查詢報告後才做；不這樣分，002 重跑會再卡在這一步，根本產不出書狀 |
| 查證過關與否由程式判斷，沒過就明確回報失敗 | 原本查證指令不管結果都回「成功」，只有通過的才留紀錄；過沒過要靠 AI 自己看 |
| 連線失敗自動重試；重試還失敗就標「連線錯誤」，和「查無」分開 | 兩案各有一條法律因為暫時的連線錯誤失敗，靠 AI 手動重試才過 |
| 查證結果只能透過固定指令寫入該案的紀錄，不能直接改共用資料 | 002 的查證 AI 直接改了共用資料，連帶改到 001 看到的狀態 |
| 法條在每一輪落地時就檢查能不能查證 | 民法債編施行法從第一輪一路引用到評估，到最後查證才發現系統不支援 |

### 9. 書狀 ✅ 已定案

| 改什麼 | 為什麼 |
|---|---|
| 起訴狀只用原告最後一輪的「我方主張本身」和已主張的項目，不用反駁、內部備註、準備清單、待確認項目 | 起訴狀是打官司的第一份文件，那時被告還沒開口。原本拿原告最後一輪的反駁來寫，002 起訴狀第一段就寫「被告主張…」，003 連被告口吻的「本方」都還在 |
| 起訴狀出現「被告主張／被告抗辯／被告自承／本方／對造」，或「Stage／輪次／法官訊問」這類模擬流程用語，程式擋下 | 用程式守住，不靠 AI 自律。換成 Codex、用真實案件跑，001 起訴狀還是出現「正面回應對造最強論點」「Stage 2 要求補明的原起訴」，用的字是「對造」，原本列的字樣擋不到 |
| 不再規定「把最後一輪原文直接套進書狀」 | 001 那句就是照這條規定原封不動搬進起訴狀的 |
| 001 那份起訴狀留下來當固定測試，改完必須擋得下 | 002 原本沒產出書狀，前後沒得比；001 是換模型、真實案件後唯一實際發生的案例 |
| 骨架版不預先回應可預見的抗辯 | 一寫就會提到被告的說法，程式分不出是「預先回應」還是「被告已經說過」；預想和應對已在內部備註，由律師決定要不要寫 |
| 起訴狀附請求金額明細：每筆的名目、金額、依據（事實編號或計算式）、對應主張；程式加總比對請求金額 | 原本沒有任何一步核對金額 |
| 還在待確認的項目，金額不進訴之聲明，改列「律師附註：待確認後再決定是否請求」 | 003：可能拿不到的一個月預告工資被直接算進起訴狀 |

### 跨步驟：流程改由程式控制 ✅ 已定案

報告前只做一半：規則改由程式檢查（例如撤回沒附依據就拒收），給對手的摘要、角色讀的案件檔、查證清單、回報都改由程式產生，不再讓 AI 轉述。完整的「程式控制整條流程」（每一步由程式依序呼叫、驗證輸出、存紀錄）留到報告後。

## 怎麼確認改了有效

用同一件真實案件（real-002）、同一個模型重跑，和改之前的紀錄比較。指標在跑之前先定好，例如：時效和第182條抗辯最後是「待確認」還是「撤回」、引用查證有沒有通過（第205條應標「版本未查證」）、起訴狀有沒有出現被告才會說的話。

- 起訴狀的部分 002 原本沒有可比的書狀，所以另外用 001 那份起訴狀當固定測試，證明程式擋得下。
- 重跑時案件輸入只做最小轉換：標明代理原告，事實原樣放進原告欄，聲明拿掉「原起訴」字樣。輸入格式也變了，這點會列為比較的限制。

單案只能看方向，不是統計結論。
