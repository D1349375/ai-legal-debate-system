# 法官轉述當事人說法:作法調研與之後的方向

2026-11-03 整理。起因是 C1 實跑:法官沒用四個硬擋詞,改寫「你方自己也寫」「自己指出」,還有 1 處沒引述的「承認」,全部通過 M12 的自承檢查。這份記錄:這類問題業界怎麼處理、決賽前做什麼(T10、T11)、實跑次數變多之後要依數據決定什麼。

## 1. 問題是什麼

要防的不是某個用詞,而是**轉述錯誤**:法官寫「某方說了或承認了 Y」時,要確認(1)那一方真的說過,(2)原句的性質沒被改掉(主張、假設、自我評估、資料缺口)。

- 「自認」在民事訴訟有法律效果(民訴第 279 條),律師讀到「被告自承」會以為對方讓步。
- 早期錄製的評估出現過「被告誠實承認過失相抵抗辯…」「與被告 Stage 3 之自我承認相互印證」(M12 的起因,見 `main-finals-fix-list.md`)。
- 研究上的對應名稱:史丹佛評測法律 AI 的論文把「附了出處但出處不支持說法」列為一種錯誤;對話摘要的錯誤分類列了「說話者錯置」與「觀點被寫成事實」。

## 2. 業界與研究的做法

| 做法 | 例子 | 準確度與限制 | 適合 |
|---|---|---|---|
| 關鍵字擋詞 | 內容過濾的黑名單 | 同義詞、換句話說就繞過;詞越多誤擋越多 | 只當最低限度 |
| 結構化輸出 + 程式比對原文 | Anthropic Citations API 回傳 `cited_text`;資料擷取要求每個值附原文片段,程式確認,分「已驗證、失敗、無法驗證」 | 結果固定;只能確認原文存在,不能確認解讀正確 | 可以硬擋 |
| 語意檢查 | 蘊含模型(AlignScore)、另一個模型當裁判(NeMo Guardrails、Guardrails AI) | 中等。Vectara 的評測裡 AlignScore 約 65% 準確;NVIDIA 文件寫明效果取決於模型有沒有照指示做 | 警告、提示人工,不硬擋 |
| 拆成原子主張逐條驗 | FActScore、VeriScore | 較準,但慢又貴 | 事後評估 |
| 分層 | 便宜、結果固定的檢查在前,模型判斷在中間,人在最後 | — | 一般建議 |

法律工具的情況:接了檢索資料庫的法律 AI(Lexis+ AI、Westlaw AI)在那篇評測裡仍有約六分之一到三分之一的問題答錯。業界常態不是宣稱零錯誤,而是讓錯誤容易被看見、讓律師容易核對。

**法院自己的做法最值得借鏡**:準備程序整理爭點時(民訴第 270 條之 1),法官列出不爭執事項並當面確認;當事人明確表示沒有意見,才依第 279 條算自認。也就是說,「自認」來自程序上的確認,不是從文字推論。

## 3. 本專案現在的防線

| 層 | 做法 | 狀態 |
|---|---|---|
| 1. 隔離來源 | 自我檢討寫進內部檢討段落,法官讀不到(M15) | 有;C1 段落外仍漏 2 句,其中 1 句被法官引用 |
| 2. 範本指示 | 法官範本禁止把假設、自我評估寫成承認 | 有;C1 有 1 處「承認」違反 |
| 3. 程式硬擋 | 四個詞必須附可查證的原句(M12、T3) | 有;換詞全部漏掉 |
| 4. 人工抽查 | V35 逐句看 | 有,但只在我們實跑後做,律師在畫面上沒有對照工具 |

決賽前要做的兩項:

- **T10**(第 3、4 層之間):把法官轉述的句子找出來分級(引號逐字、近似、在另一方、找不到;未引述的「承認」),在 UI 讓律師對照原文。只警告,不擋。見 [T10](T10-attribution-review.md)。
- **T11**(第 1 層):Stage 2、3 範本的受挫評估移進內部檢討段落,減少法官讀到的自我評估。見 [T11](T11-public-self-review-template.md)。

C1 的雛形量測顯示:引號逐字檢查單獨做,在 C1 上只會找到 6 處「近似但不逐字」,意思都沒變;兩個實質問題(未引述的「承認」、段落外的「法院採對造說的風險高」)它都抓不到。所以 T10 加了未引述「承認」的警告,段落外自我評估交給 T11。

## 4. 實跑次數變多之後要決定的事

單次實跑只看方向(SKILL「落地紀律」)。以下各項要等累積夠多次實跑才決定。建議至少同一案件 5 次以上、不同案件 3 件以上,而且每次都照下面的欄位記錄。

### 4.1 每次實跑要記錄的數字

在 `docs/live-run-records/` 每次的紀錄裡固定記:

| 欄位 | 用途 |
|---|---|
| 法官輸出的四個硬擋詞處數、不成立數(V35) | 硬擋是否還有作用 |
| 換詞處數(「自己指出」「自己寫明」等)與人工判斷 | 換詞的頻率與危害 |
| T10 各分級數量、警告的人工判斷(該警告 / 誤報) | 算精確率,決定能不能升級 |
| 段落外自我評估句數(人工)、T4 警告數 | 算 T4 漏報率,看 T11 有沒有效 |
| 法官引用段落外自我評估的次數 | 最直接的危害指標 |
| 分類器中止次數 | 內部檢討段落是否增加中止 |
| `check-judge` 退回次數 | 硬擋是否造成重派成本 |

人工判斷的結果同時就是之後評估語意檢查的標註資料,要保留句子與判斷(不放語料全文的話,至少保留案件 ID、位置與判斷)。

### 4.2 依數據決定

| 要決定的事 | 判斷依據 | 傾向 |
|---|---|---|
| T10 的 `missing`、`other_side` 要不要改成硬擋 | 多次實跑誤報接近 0 | 只有這兩級可能升級,因為比對原文是結構性的;`close` 與未引述「承認」維持警告 |
| `close` 的門檻 | 人工判斷近似是否都「意思沒變」 | 調門檻,不加詞 |
| T4 詞表要不要保留 | T11 之後段落外自我評估是否接近 0 | 接近 0 就維持現狀不再補詞;沒改善就檢討範本,而不是補詞 |
| 內部檢討段落是否增加分類器中止 | 中止次數和 #4(1 次)、W0、C1(0 次)比 | 中止變多才考慮改段落標記方式 |
| 雙方論證也做轉述核對 | W0 的 F4(原告把被告的條件句稱為自承)是否常見 | 常見就把 T10 延伸到論證,只警告 |
| 加語意檢查(蘊含模型或模型裁判) | 用 4.1 累積的標註資料量精確率 | 只當警告、放在查證步驟;精確率不夠就不加。不用中國機構開發的模型 |

### 4.3 新架構(`pleading-exchange`)的方向

這是比詞表更根本的做法:讓「承認」變成資料,而不是文字。

1. **自認只來自明確表態**:答辯狀逐點表態(承認、否認、不知)。組員 W5 已規定不爭執事項必須指向被告標了承認的事實點(`engine/issue_sheet.py`)。延伸到評估:法官要寫某方承認了什麼,必須附事實點編號,程式比對該點的表態。
2. **轉述附欄位**:法官評估輸出時,每個轉述附 `{side, 來源(論證或事實點編號), 原句, 性質}`,程式比對原句與性質(性質欄位命名要避開共同規則第 8 點的禁用字)。這是 Citations API 那類作法。
3. **推論改成發問**:法官覺得某方讓步時,不寫「被告自承」,改在訊問問「你方是否爭執 X?」,由該方明確回答。對應法院確認不爭執事項的程序。
4. **律師核對介面**:轉述句旁邊直接顯示原文;律師可以標「轉述正確 / 錯誤」,累積成標註資料。

## 5. 對外說法

- 可以說:最明確的法律用語(自承、自認、自陳、坦承)由程式檢查原文;其他轉述會標示出來,由律師對照原文判斷。
- 不能說:程式保證法官不會把假設當成承認;擋詞擋得住換句話說。
