## 1. 自承檢查認錯說話的人(`9e9202f`)

**問題**:`admission_sources` 沿用舊流程,把 `facts_summary` 當成雙方共同的事實。v2 的事實經過是原告律師寫的,兩個方向都錯:

- 法官可以從事實經過抄一句,寫成「被告自承『原告於某日匯款100萬元』」,檢查放行。
- 分析範本規定「被告自承」要引用「對方已知反應」的原句,但檢查從來不把這個欄位當來源,照範本寫反而被擋。W5 法官落地是硬擋,會卡住流程。

**改法**:`database/db.py` `admission_sources`:v2 案件的事實經過只算原告的話,對方已知反應算被告的話。舊案件不變。

**驗證**:新增 3 個測試,改前 2 個失敗(正好是上面兩點)。

## 2. 主 agent 只交接檔案路徑(`f985944`)

**問題**:主 agent 的上下文每一輪都整份重讀。舊流程 run-4 主 agent 112 輪,從 3.1 萬 token 長到 19.3 萬,約佔全程輸入 token 八成(每個子 agent 最多約 5 萬)。不是單一大檔造成的,而是每派一個 subagent 固定多約 1 萬:回覆的 JSON 進來一次、主 agent 再自己 Write 成檔一次、先 Read 範本再整份貼進派工指示。v2 的 subagent 比舊流程多,照舊做法只會更膨脹。

**改法**:大段內容不經過主 agent。

| 原本 | 改成 |
|---|---|
| 主 agent 讀範本、填佔位符、整份貼給 subagent | `python main.py prompt <範本> --out <檔> --set KEY=VALUE` 由程式填好寫成檔,只印路徑;subagent 自己讀。佔位符沒填完或填錯名字直接拒絕 |
| SKILL.md 手貼一段 P1 檢索規則(寫著「組員的指令還沒做好」) | `prompt --phase p1 --side plaintiff --case-dir <案件資料夾>` 由程式帶入 `retrieval-rules` 的輸出與該角色的快照、紀錄路徑 |
| subagent 回整份 JSON,主 agent 再寫成檔 | 範本用 `{OUTPUT_PATH}`:subagent 自己寫檔,只回一行「已寫入 …」,有檢索被拒時同一行加次數 |
| 主 agent 替分析 JSON 補 `case_id`、`stage` | 範本的輸出格式直接含這兩欄,主 agent 不碰模型產出 |
| `role-view`、`public-args` 印整份 JSON 再由主 agent 存檔 | 加 `--out <檔>`,只印路徑 |

改到的檔案:`main.py`、`templates/stage1_prompt.txt` 與 `complaint_prompt.txt`(只改最後的輸出說明)、`SKILL.md` Step 1–3 與新的「派 subagent 與交接檔案」一節。

**驗證**:新增 4 個測試;實跑見第 4 節。

## 3. P4、P5、P6 的對手資料改成書狀(`9350291`,只改規格與計畫)

**問題**:規格 5.6 寫「對手資料維持結構化摘要,同現行 Step 4」。舊 Step 4 從 `public-args` 摘對造的 stage 1。v2 的 stage 1 是 P1、P2 的分析,不是書狀;原告分析的公開段落仍有事實經過與沒列進起訴狀的證據。被告在 P2 只讀起訴狀,到 P4 卻會從摘要讀到這些,隔離就破了。規格 5.7 讓 P6 法官讀 `public-args`,同樣等於間接讀了事實經過,和 5.5「法官不讀 `facts_summary`」矛盾。

**改法**:
- P4:原告拿模擬答辯狀與逐點表態,被告拿律師確認版起訴狀,雙方都拿爭點整理表與闡明。
- P5:另給對造 P4 的摘要,只摘對造 stage 2。準備書狀本來就送達對造,寫進去的事實可以給。
- P6:法官讀雙方 stage 2、3 與 `finalize --for-judge`,不給 stage 1。
- 計畫 W6 的陷阱說明同步,並要求用哨兵字串測被告在 P4 讀不到事實經過。

## 4. 第一次實跑後的兩個修正(`6d1b8b5`)

實跑 P1 一次(有證據清單,W2 兩次都沒有),交接檔案這套模型有照做。另外抓到兩件事:

- **主 agent 誤報「沒有證據清單」**:第 2 節之後主 agent 不讀角色檔,不知道有沒有證據,SKILL Step 1 第 4 點又要它回報,就猜錯了。改成用 Grep 在角色檔找 `"evidence": []`。
- **退回時交不回同一個 subagent**:無人值守執行裡 `SendMessage` 不能用。SKILL 寫明改成另開新 subagent,讀同一個派工檔、既有輸出與報錯原文,仍算同一份輸出的退回次數。

## 5. P1 分析只搜不讀判決全文(`1872747`)

**問題**:第一次實跑,起訴狀最後只引用的 3 份判決,全文被讀了 14 次:

| 誰 | 讀幾次 | 必要嗎 |
|---|---|---|
| 分析 | 6 | 不必要:分析的輸出沒有摘句,讀了也交不出去,其中一半撰狀又重讀 |
| 撰狀 | 3 | 必要:逐字摘句 |
| 查證 | 3 | 必要:獨立核對 |
| 改寫後新的查證 | 2 | 不必要:改寫只刪掉一份,沒變的又重讀 |

每個 subagent 是獨立對話,讀過的全文留在自己的上下文,之後每一輪都重讀。分析是跑最多輪的 subagent(28 輪,上下文到 10.6 萬)。

**為什麼要讀全文**:防兩件事:確認判決真的支持要件;摘句要知道是誰說的(當事人主張、原審見解還是最高法院自己的判斷)。真正需要的是會引用的撰狀與會核對的查證,不是分析。

**改法**(沒有新程式):
- P1 檢索規則(`engine/retrieval_rules.py`):分析只搜不讀,候選判決寫在公開論證並標「待撰狀讀全文」;讀全文是撰狀的步驟。
- 分析範本:`cited_precedents` 給空陣列。
- SKILL Step 3:改寫只刪除引用時沿用原本的 `citation_review.json`(落地只核對起訴狀現有的判決,多的會被忽略);有新增引用才只查新增的。

也考慮過讓 `judgment` 只印最高法院的理由段。沒做:要寫切段程式、可能切錯,「上訴駁回」的判決本院段常很短,查證也必須看全文。刪掉一次重複的讀取比新增功能簡單。

**驗證**:第二次實跑,同樣輸入:

| | 第 1 次 | 第 2 次 |
|---|---:|---:|
| 花費 | 2.94 美元 | 2.07 美元 |
| 分析 subagent 上下文最高 | 10.6 萬 | 6.3 萬 |
| 判決全文讀取 | 14 次(落地引用 2 份) | 10 次(落地引用 5 份) |
| 主 agent 上下文最高 | 5.5 萬 | 5.0 萬 |
| subagent | 6 | 4 |

副作用:撰狀在正文提到分析列的候選判決卻沒讀、沒列進 `citations`,`complaint --check` 擋下,改寫一次通過。

## 6. 合併時要注意

- **SKILL.md Step 1–3** 改動最多。W3 若也改了 Step 3 附近(例如停止點),合併時以這裡的交接方式為準,再加上 W3 的內容。
- **W4 起的新範本**(被告分析、答辯狀、法官、改寫)照第 2 節:輸出寫進 `{OUTPUT_PATH}`、只回一行,用 `main.py prompt` 產生派工檔。接手文件第 7 節有寫。
- **P2 被告分析**同樣建議只搜不讀,讀全文留給答辯狀撰狀。`retrieval_rules.py` 的 P2 規則還沒改。
- `v2-flow-fixes` 只碰 P1;舊流程借用的範本(Step 4 以後的過渡)沒動,那些等 W4–W7 換掉。

## 7. 沒做或沒驗證的

- 只實跑兩次,都只到 P1,單案,不是統計。沒有在 UI 按鈕上跑(還沒有 `stop_after`)。
- W2 的原始輸出不在這台電腦,主 agent 上下文和 W2 沒有同口徑對照。
- 查證 subagent 在理由裡寫的提醒(例如「摘句出自本院維持的原審理由」「命題比判決略強」)有存進 `structured_json.citation_review`,但畫面沒顯示,落地也只看 true/false。
- 事實點把原告主張寫成直接陳述(W2 的 CF5、這次的 CF7)仍在,屬於 W7。
- `build_prompt` 的舊寫法(`{CASE_FACTS_PATH}` 填 `case.json`、要求執行 `issues`)留給 W3、W4。
