# 系統架構

> 本文件為 [`docs/en/architecture.md`](../en/architecture.md) 的中文版。
> 內容取自原「產品開發報告」的技術章節，商業化與變現分析已移出本 repo。

本系統結合既有的兩大技術底層——零容錯內容查證體系與多 Agent 結構化辯論引擎——並導入蒸餾出的
`taiwan-legal-pleading` skill，承載台灣訴訟文書的實務寫法慣例。

重點不是模板填空：**在產出任何草稿之前，先讓原告律師 Agent 與被告律師 Agent 針對本案進行結構化
攻防演練**，抓出合規漏洞與本案最脆弱的死穴，然後才進入撰狀。

---

## 一、三引擎架構

### 引擎一 — 知識與零容錯查證

解決 LegalTech 工具的第一個典型失敗：編造聽起來很像真的法條與裁判字號。

- **法規**：民法、公司法、勞動基準法、消費者保護法、刑法五部全文，以程式解析全國法規資料庫
  (`law.moj.gov.tw`) 取得。**刻意不用 AI 摘要**——初期嘗試以會將內容送進小模型摘要/改寫的抓取
  工具擷取，判定對查證用途不可接受，改為直接抓原始 HTML 再以程式解析，確保逐條全文一字不差。
- **判決**：最高法院民事裁判，先比對本地種子語料庫作為加速路徑，未命中則即時查證司法院裁判書
  查詢系統 (FJUD)，使查證範圍不受限於本地語料庫既有內容。
- **快取永遠不是權威來源**：`corpus/` 只是比對用的加速層，法條一律回頭比對官網原文，不直接
  信任快取內容。

實作見 `engine/verify.py`，比照 `draft → fact_checked → published` 三態治理流程。

### 引擎二 — 多 Agent 模擬攻防

解決第二個失敗：Agent 換個人設卻只是互相附和。

- **原告律師 Agent**：最有利的主張、請求權基礎、損害賠償計算。
- **被告律師 Agent**：免責條款、程序瑕疵、對方舉證漏洞。
- **法官 Agent**：主持庭期、整理爭點、訊問雙方。

R1 獨立盲判、R2 結構化反駁——後者強制正面回應對手最強論點，並寫出自己的 falsifier（退讓條件）。
聚合為純程式碼機械執行，模型不得推翻（`engine/aggregate.py`）。

防止多 Agent 趨同的完整對策見
[多 Agent 系統同質化問題](multi-agent-homogenization.md)，檢索端的隔離規格見
[立場隔離 RAG 檢索架構](stance-isolated-rag-spec.md)。

### 引擎三 — 訴狀蒸餾

解決第三個失敗：產出的文字完全不像可以遞狀的東西。

蒸餾出的 know-how 分三塊：

- **訴狀結構骨架**：明確區分「訴之聲明」「請求權基礎」「事實與理由」「證據清單」，且「事實與
  理由」嚴格遵循法理三段論推進。
- **法言法語表達 DNA**：採用正統連接詞與開頭（`按…定有明文`、`次查…`、`再查…`、
  `揆諸前揭最高法院判例意旨…`），避免白話文或翻譯腔。
- **避坑與法院禮儀規範**：自動將情緒化用語校正為法律專業修辭（「對方無恥不還錢」→「被告所辯
  顯係推諉卸責之詞，殊無足採」），並確保標註管轄法院與訴訟標的金額。

## 二、蒸餾與檢索必須分離

**蒸餾只萃取「怎麼寫」的抽象規律，不記憶「判了什麼」。** SKILL.md 中只保留結構、語氣、三段論
邏輯規則，不嵌入完整判決書原文。

若把完整判決書當 few-shot 範例塞進 Prompt，會產生兩層問題：**錨定偏誤**，Agent 把新案件事實套用
進記得的舊案模式；以及**資料污染**，讓日後用同一批判決書驗證系統準確率的測試完全失真——如同
學生拿背過答案的考卷驗收學習成果。

因此蒸餾語料、RAG 即時檢索語料、驗證測試集三者必須完全隔離。完整說明見
[自建法學資料庫：蒸餾污染風險與資料價值驗證機制](corpus-contamination-and-validation.md)。

## 三、端到端流程

1. **資訊輸入**：用戶以白話描述糾紛經過，並上傳相關合約或往來紀錄。
2. **法理與判例匹配**：系統透過查證引擎調取台灣現行法條與相關最高法院判例。
3. **模擬攻防辯論**：原告 Agent 提出論點，被告 Agent 於 R2 依免責條款反駁；系統標註本案最大的
   兩個舉證弱點與建議補充之證據。
4. **訴狀生成**：調用 `taiwan-legal-pleading` skill 產出符合司法院格式之初稿。

## 四、工程進度

- **Phase 0 語料：2/3 完成。** 五部法規全文（`corpus/statutes/`）與最高法院民事裁判
  （`corpus/judgments/`，經官方開放 API 取得）皆已到位。**唯一剩下的阻塞項是
  `corpus/pleadings/`**（20 份真實去識別化訴狀），這是人脈/取得管道問題而非工程問題，仍待律師
  Design Partner。
- **Phase 1.1（專案骨架）與 1.3（法規/判例查證引擎）已完成並通過測試**：`database/schema.py`、
  `database/db.py`、`engine/aggregate.py`、`engine/verify.py`、`main.py` 六個 CLI 子命令皆已
  實作，測試全過（含實際連線官網的整合測試），並跑過一次完整端到端煙霧測試（案件輸入→雙方
  三階段攻防→法官訊問→機械彙整→查證→判決→訴狀，含 write-once 與查證閘門的失敗路徑驗證）。
- **Phase 1.2（`taiwan-legal-pleading` 蒸餾）仍卡在 Phase 0 訴狀語料**，尚未開始。
- **Phase 1.4（legal-debate orchestrator skill，四階段 prompt 模板）尚未開始**——這是唯一需要
  agent runtime 實際扮演原告/被告/法官角色的部分。

**架構修正（2026-08-06 已確認）**：法官角色已收進 Phase 1 核心（原告代理人/被告代理人/法官
三角色，單一模型），非「全角色模擬法庭」報告所述之後期旗艦擴充；異質模型矩陣與資訊不對稱切面
延後至 Phase 3，觸發條件為 Phase 2 律師實測觀察到雙方論點趨同，非排程到了就做。

## 五、已知技術風險

**文件層級檢索錯配（DRM）**：台灣判決書高度制式化行文，容易導致檢索抓錯來源判決書（文獻在同類
材料上實測錯誤率超過 95%）。這是產品能否被律師信任的底線問題，須以摘要增強分塊法處理，見
[RAG 系統設計報告](rag-system-design.md)。

**法律合規硬限制**：《律師法》第 127 條對非律師收費代寫訴狀有 3 年以下有期徒刑之刑責。這是本
專案定位為律師內部工具而非消費者服務的原因，是架構上的硬限制，不是市場偏好。

**事實認定**：AI 能辯論法理，但無法替用戶採集實體證據。輸入之事實不完整，攻防與訴狀亦為
garbage out。

**Token 成本**：多 Agent 辯論加判例檢索單次消耗約 30~50 萬 tokens。

**產出品質驗證**：不需要聘律師全樣本審核——判決書本身已寫明誰勝訴、賠多少、爭點為何，可直接
當 ground truth 做自動化比對（結果準確率／爭點命中率／引用真實性），僅將自動化指標篩出的
5-10% 邊界案例交真人律師審核。此為選配的附加功能，非上線之必要條件，但能加速取得律師設計
夥伴的初始信任。見
[自建法學資料庫：蒸餾污染風險與資料價值驗證機制](corpus-contamination-and-validation.md)。
