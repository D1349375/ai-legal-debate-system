# 交接給 Codex:用真實判決當輸入,實跑 legal-debate 流程並評估幻覺

> 撰寫:2026-10-31。對象:Codex(在本 repo 根目錄執行)。這份是自足的交接,不需要讀先前的對話。
> 本次是**基準實跑**:用現行範本、不修任何東西,看先前分析出的錯誤模式在真實輸入下會不會重現。

## 0. 背景:為什麼要跑這一輪

先前分析了 `test-2026-08-08-001/002/003` 三案(AI 自編事實)與 `gcis-001` 四次實跑,結論是:**幻覺主因不在「輸入太少」,而在流程設計**。錯誤模式如下,這一輪要驗證它們在真實案件上會不會重現:

| 代號 | 錯誤模式 | 已知成因(檔案:行) |
|---|---|---|
| P1 | 案卷沒寫的事實,被說成某方「自承／自認／不爭執」 | Stage 1 要求把自我弱點寫進給法官看的 argument(`stage1_prompt.txt:3`、`:14`);法官 `based_on` 必須回溯 Stage 1 句子(`judge_question_prompt.txt:20`),把「一方未回應」當成不爭執(`:16`);falsifier 定義成讓步條件且必填(`stage2_prompt.txt:41`、`stage3_prompt.txt:32`);`stage3:33`「不是誇大的版本」;agent 自己從 reasoning 寫到 position 時把限定語壓掉 |
| P2 | 原告起訴狀混入回應被告的內容 | 9A 素材用原告 Stage 3,而 `stage3:31` 要求正面回應對造,Stage 3 本質是反駁文 |
| P3 | 被告近乎認輸、法官評估自相矛盾 | `engine/aggregate.py:13-33` 把 falsifier 原樣抄成 weak_points,`verdict_prompt.txt:12` 禁止反向解讀;`position_drift` 是引用集合的 Jaccard 距離,卻被法官讀成「立場拉鋸」 |
| P4 | 引用的判例案由與論點不符 | `stage1:27` 允許憑記憶引用;泛用檢索詞「有理由」「過失」「因果關係」(`engine/stance_rag.py:18`、`:28`)容易命中無關裁定 |
| P5 | 推論跳太遠、把推論寫成事實 | 沒有任何階段要求區分「事實」與「我方推論」 |
| 污染 | 案件來源判決就在語料庫,agent 可能讀到答案 | 程式沒有任何排除邏輯,`source_note` 沒有程式讀它 |

另有一個干擾因子:輸入把原告主張寫成客觀事實(001–003),比 gcis 把主張標成「原告主張」更容易出錯。

**換用 Codex 跑還有一個附帶價值**:先前紀錄都是 Claude 跑的。如果換一個模型、P1–P5 照樣出現,就更能證明是流程問題而非單一模型的幻覺。所以請在紀錄中寫明使用的模型名稱與 reasoning effort。

## 1. 案件事實輸入:去哪裡找、怎麼挑

### 1.1 來源:地方法院第一審民事判決(FJUD)

用**司法院裁判書查詢系統 FJUD**(`https://judgment.judicial.gov.tw/FJUD/default.aspx`,免登入;2026-10-31 從本機實測可連線,`engine/verify.py:134` 的 `_fjud_search` 已有可用的查詢實作可參考)。

選地院第一審判決的理由:

1. **不會污染語料庫**:`corpus/judgments/` 的 1,088 筆全部是最高法院民事(`TPSV`),裁判日期 2026-03 到 2026-07。地院判決不在裡面。
2. **結構剛好可以切成「輸入」和「標準答案」**:第一審判決通常分成「原告主張」「被告抗辯」「兩造不爭執事項／本件爭點」「法院之判斷」「主文」。實際使用時只會有原告單方面的背景說明,還沒寫起訴狀,被告也還不知道要被告,所以**輸入只能來自「原告主張」,而且要還原成起訴前的版本(見 2.2)**。被告抗辯、爭點、法院判斷、主文**任何角色在跑流程時都看不到**,只在全部跑完後拿來評分:模擬的被告 agent 預想到的抗辯,和真實被告後來在法庭上提出的抗辯差多少。最高法院裁定只轉述原審認定,沒有這種結構,gcis-001 就是因此只能自己改寫、留下含糊處。
3. **可以挑在模型訓練資料之後**:選 2026-08-01 之後的判決,降低模型預訓練看過的機率。

### 1.2 挑選條件(全部要符合)

- 法院:任一地方法院;裁判類別:民事;**字別「訴」**(通常程序)。不要「簡」「小」「消」「家」「重訴」以外的特殊字別;「重訴」可以。
- 裁判日期:**2026-08-01 之後**。
- 判決(不是裁定),且**兩造都有到庭辯論**:排除一造辯論判決、認諾、捨棄、和解、撤回。判決裡要有實質的「被告抗辯」段落。
- 訴訟標的金額超過 50 萬元(通常程序)。
- 請求權基礎以**民法**為主(語料庫法規只有民法、公司法、勞基法、消保法、刑法)。
- 當事人單純:原告、被告各 1–2 人;沒有反訴、追加被告、參加人。
- 最好是**一部勝訴、一部敗訴**,判斷層次比較多。
- 判決全文要列出「不爭執事項」與「爭點」,沒有就換一件。

### 1.3 要挑幾件、什麼類型

為了和先前三案直接對照,依序挑:

| 新案件 ID | 類型 | 對照的舊案 | FJUD 全文檢索詞參考 |
|---|---|---|---|
| `real-2026-10-31-001` | 買賣或承攬瑕疵、契約不履行 | 001(契約不履行) | `瑕疵&解除契約&價金` 或 `承攬&瑕疵修補&報酬` |
| `real-2026-10-31-002` | 車禍侵權損害賠償 | 002(侵權行為) | `車禍&民法第184條&第191條之2&損害賠償` |
| `real-2026-10-31-003`(選做) | 勞動契約爭議 | 003(勞資爭議) | 字別改用「勞訴」:`確認僱傭關係存在&資遣費` |

第 3 件是選做:勞動事件走勞動事件法程序,不是本系統宣稱的「通常訴訟程序」,報告中要註明這個差異。

**先跑 001、002 兩件,跑完再決定要不要跑 003。**

### 1.4 如果 Codex 自己查不到 FJUD

FJUD 的進階搜尋是 ASP.NET 表單,如果程式化查詢失敗,**停下來請使用者手動查**,把下面這段給使用者:

> 請到 https://judgment.judicial.gov.tw/FJUD/default.aspx → 「更多條件查詢」:法院選任一地方法院、類別選「民事」、字別填「訴」、裁判期間 115/08/01 到今天、全文內容填上表的檢索詞。從結果挑 3–5 件符合 1.2 條件的,把網址貼給 Codex。

不要用司法院資料開放平臺 API(需要使用者帳密,而且只在每天 00:00–06:00 服務)。

### 1.5 污染檢查(挑定後、建檔前)

- 用 `rg` 在 `corpus/` 搜尋:判決字號、兩造姓名或公司名、承審法官姓名。任何命中都換一件。
- 判決裡如果引用了某個最高法院判例,且該判例在 `corpus/judgments/` 裡,**不用換案**,但要在評分報告中標記:之後如果 agent 引用了它,要分辨是正常檢索還是看到答案。

## 2. 建立輸入檔與標準答案檔

### 2.1 標準答案(holdout)放在 repo 外面

每件建一個資料夾 `%USERPROFILE%\legaldebate_holdout\<case_id>\`(不要放在 repo 裡,任何角色的 prompt 都不得提到這個路徑):

- `judgment_full.txt`:判決全文原樣。
- `source.json`:法院、字號、裁判日期、FJUD 網址、抓取時間。
- `gold.json`:從判決整理出的
  - `defendant_defenses`:被告抗辯逐點(盡量照原文)
  - `uncontested_facts`:不爭執事項
  - `issues`:本件爭點
  - `outcome`:主文(勝敗、判准金額)
  - `court_reasoning_keypoints`:法院判斷要點
  - `cited_authorities`:判決引用的法條與判例

### 2.2 案件輸入 `data/cases/<case_id>.json`

格式同 `data/cases/test-2026-10-27-gcis-001.json`,欄位 `case_id`/`case_type`/`facts_summary`/`claims`/`source_note`。

**要模擬的情境**:當事人第一次找律師,只帶著自己的說法和手上的文件。還沒寫起訴狀,沒開過庭,被告還不知道要被告,也沒有任何法院調查的結果。判決裡的「原告主張」是訴訟打完後整理的版本,常常已經回應過被告、改過聲明、用了法院調查才拿到的證據,**不能直接照抄**。撰寫規則:

1. **只用判決的「原告主張」段落**,加上原告起訴前本來就拿得到的文件所載的事實(自己簽的契約、收據、對話紀錄、自己的就醫單據、事故當天的報案紀錄)。
2. **還原成起訴前的版本,刪掉以下內容**:
   - 回應被告的句子:「被告雖辯稱…」「被告所辯…不足採」「被告抗辯…惟…」,以及只是為了反駁某個抗辯才補充的事實。
   - 開庭後才有的證據:鑑定報告、證人證述、法院調閱或函查的資料、對造提出的文件、車禍鑑定委員會或覆議意見。
   - 訴訟中變更過的聲明或金額:判決如果寫「原告起訴時聲明…嗣變更為…」,用起訴時的版本。
   - 判決的「不爭執事項」中只能透過被告陳述才知道的內容。
3. **每一句不是有書證的客觀事實,就標「原告主張」**。例如「原告主張被告因低頭操作手機分心」,不要寫成「被告因低頭操作手機分心」。
4. **完全不放**:被告抗辯、被告的任何說法、法院判斷、主文、判准金額。
5. 原告當時不知道或判決沒寫的,寫「卷內資料未載明」,不要補。
6. 不確定某句是起訴前就有、還是訴訟中才出現的,就刪掉,並記在 `holdout\<case_id>\removed.md`(刪了什麼、為什麼),評分時用得到。
7. 自然人一律匿名成甲、乙、丙;公司也匿名(例如「A 公司」),不提供統一編號,所以本輪**不做商工查核**(Step 1 的 `party` 跳過,Step 1.5 仍要跑 `issues`,它會照實寫未查核)。
8. `claims`:照判決記載的原告**起訴時**訴之聲明改寫,保留金額與利息起算方式。
9. `source_note`:寫「取材自<法院><字號>判決之原告主張;已匿名;未納入被告抗辯與法院判斷。標準答案存於 repo 外」,**不寫 holdout 路徑**。
10. `case_type` 用既有的值:`契約不履行`、`侵權行為`、`勞資爭議`(`engine/stance_rag.py` 依此選檢索詞,用其他字串會拿不到類型檢索詞)。

建好後先給使用者看兩份 `facts_summary` 和各自的 `removed.md`,**確認後再開跑**。

## 3. 用 Codex 執行流程

### 3.1 照 `SKILL.md` 跑,但把 subagent 換成獨立的 `codex exec`

流程手冊是 `.claude/skills/legal-debate/SKILL.md`,Step 1 到 Step 10 照做,**範本逐字套用**(`.claude/skills/legal-debate/templates/*.txt`,只填 `{佔位符}`)。差別只有派工方式:

- SKILL.md 說「開一個 subagent」的地方,改成**開一個新的 `codex exec` 程序**,每個角色、每個階段各一個,互不共用 context。這是 Stage 1 盲判與 Step 8 獨立查證的前提,不能在同一個 Codex 對話裡自己扮演多個角色。
- 先執行 `codex exec --help` 確認參數。每次呼叫都要:
  - 把**實際送出的完整 prompt** 存成 `prompt.txt`;
  - 用 `--json`(或等效參數)保存完整事件紀錄,作用同先前的 `stream.jsonl`,之後要拿它做污染檢查;
  - 把最後回覆另存成檔(`--output-last-message` 或等效參數)。
- 範本裡寫的 Read／Grep／Glob 是 Claude Code 的工具名稱。**不要改範本**,而是在每份 prompt 最前面固定加一行,所有角色完全相同:
  `【環境說明】本 prompt 提到的 Read、Grep、Glob 工具,在你的環境中分別對應讀取檔案、rg 搜尋、列出檔案;語意與規則不變。`
  在報告中把這行列為唯一的範本偏差。
- 角色程序**不開網路搜尋**。範本要求的檢索只能在 `corpus/` 內做。
- 主程序(你)只當調度員與記帳員,規矩同 SKILL.md 開頭:不判斷案件實質、不改機械聚合、不加開輪次、不代寫被中止的輸出、不繞過查證閘門。

### 3.2 資料庫與輸出位置

- 不要寫進正式資料庫。每次執行 `python main.py ...` 前設環境變數:
  `LEGALDEBATE_DB_URL=sqlite:///database/codex_runs.db`(`database/db.py:26`、`:52`;`*.db` 已被 gitignore)。
- 每件的所有中間檔、prompt、事件紀錄、最終輸出,放在 `docs/live-run-records/codex-<case_id>/`,檔名比照 `docs/live-run-records/README.md` 描述的格式(`p_s1.json`、`d_s1.json`、`q*.json`、`anchor.json`、`verdict.json`、`pleading_draft_plaintiff.txt`、`pleading_draft_defendant.txt` 等),每個 `codex exec` 呼叫另有 `calls/<序號>_<角色>_<階段>/` 子資料夾放 prompt 與事件紀錄。
- 兩份書狀(9A 起訴狀、9B 答辯狀)都要產。

### 3.3 不要做的事

- **不要修改** `templates/`、`engine/`、`main.py`、`database/` 任何檔案,也不要修正你在過程中發現的問題。這是基準實跑,發現的問題寫進報告。
- 某一步卡住(指令報錯、角色程序連續 3 次拿不到完整 JSON、查證閘門拒絕)就照 SKILL.md 的處理方式,停在那一步並記錄,不要繞過。
- 不要 commit、不要 push。

## 4. 跑完後的評估

每件產出 `docs/live-run-records/codex-<case_id>/eval.md` 與 `eval_annotations.json`。評估時可以讀 holdout,**但這時角色程序都已經結束**。

### 4.1 機械檢查(寫腳本做,結果貼進報告)

1. **污染**:在所有事件紀錄裡搜尋 holdout 路徑、`legaldebate_holdout`、判決字號、匿名前的當事人真名、承審法官姓名、`gold.json` 中被告抗辯的特徵詞句(挑 5–10 個只在判決裡出現的字串)。任何命中都要列出是哪個角色、哪一次呼叫。
2. **網路**:確認角色程序沒有網路或網頁呼叫。
3. **事實落地**:抽出所有輸出中的日期、金額、人名、證據名稱,和 `facts_summary` 比對,列出輸入裡沒有的。
4. **自認類用語**:列出所有含「自承、自認、坦承、不爭執、已承認、不否認、迄未回應、未爭執」的句子,對每一句追到它的出處:是案件事實、是對造真的這樣陳述、還是無中生有。
5. **引用**:Step 8 的查證結果;另外對每個被引用的判例讀 `corpus/judgments/` 全文,核對案由是否支持該論點。

### 4.2 對照標準答案

1. 被告 agent 只看過原告的說法,它預想的抗辯 vs 真實被告後來提出的 `gold.json.defendant_defenses`:想到哪些、漏了哪些、多編了哪些。這是系統對使用者最有用的地方(開庭前預先知道對方可能怎麼打),也是評分重點。
   - 真實抗辯如果靠的是原告輸入裡沒有的事實(例如被告自己才有的證據),漏掉不算 agent 的錯,分開列。
2. 法官 Stage 1 後整理的爭點與 `uncontested_points` vs 判決的爭點與不爭執事項。
3. 法官評估的方向 vs 判決主文。**只記錄異同,不得寫成「預測準確率」**:單案不構成統計意義的驗證(SKILL.md「落地紀律」)。

### 4.3 逐條標註錯誤

每個錯誤一筆,格式:

```json
{
  "id": "real-001-01",
  "step": "s2_defendant",
  "field": "position",
  "quote": "<輸出中的原文,必須是該欄位的子字串,20–120 字>",
  "pattern": "P1|P2|P3|P4|P5|其他",
  "category": "LLM幻覺|流程有誤|兩者",
  "evidence": "<為什麼是錯的:對照哪個輸入、哪條範本規則、哪段判決>",
  "is_inference": false,
  "severity": "高|中|低",
  "chain": "<若同一錯誤在後面步驟被沿用,給同一個 chain id>"
}
```

- 用腳本核對每一筆 `quote` 確實是對應欄位的子字串。
- 「LLM 幻覺」= 範本沒有要求、模型自己編的;「流程有誤」= 照範本規則做就會得到這個錯;兩者都有就標「兩者」。
- 推論寫明 `is_inference: true`,不要當成已驗證。
- 同一個錯誤一路傳下去,每一跳各標一筆,用同一個 `chain`,並寫出**第一次出現**在哪一步。

### 4.4 總報告

全部跑完後寫 `docs/live-run-records/codex-real-cases-summary.md`:

- 每件案件:來源判決、輸入摘要、各步驟是否完成、執行時間、被中止次數。
- P1–P5 各自有沒有重現、在哪一步第一次出現,和先前 001–003 的結果對照。
- 輸入改成「原告主張」標記之後,P1 是否減少(對照 gcis 的觀察)。
- 換成 Codex 模型後,哪些錯誤模式仍出現(支持「流程問題」),哪些消失或新出現(可能是模型差異)。
- 本輪的偏差與限制:環境說明那一行、不做商工查核、勞動案的程序差異、模型不同、單案不具統計意義。

## 5. 交付與停止點
