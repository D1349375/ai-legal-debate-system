# 自建法學資料庫：蒸餾污染風險與資料價值驗證機制評估報告

> **報告日期**：2026-08-06
> **報告定位**：LegalDebate AI 專案技術附錄——針對「自建判決書資料庫」實作階段之兩項關鍵技術風險進行評估。
> **對應問題**：
> 1. 用公開判決書蒸餾 Skill，是否會導致律師 Agent 對判決書「有印象」進而產生偏誤？
> 2. 攻防辯論與訴狀產出資料的價值，如何在不聘請律師人工審核的前提下進行驗證？

---

## 一、報告目的與背景

專案下一階段規劃是將既有系統實際跑過台灣公開判決書，並以此結果自建資料庫，作為攻防引擎與訴狀蒸餾引擎的資料基礎。此舉在技術上會直接觸及兩個容易被忽略、但足以影響系統可信度與後續驗證有效性的問題：**蒸餾語料是否污染 Agent 判斷**，以及**如何低成本驗證系統產出是否有價值**。本報告針對此兩點進行技術性拆解，並提出可執行的架構建議。

---

## 二、問題一：律師 Agent 是否會對蒸餾用的判決書「有印象」

### 2.1 風險取決於「蒸餾方式」，不是「有沒有蒸餾」

是否會產生污染，關鍵在於判決書素材是被拿去萃取「抽象規律」，還是被直接當作「案例範本」餵給 Agent。這是兩種完全不同的技術路徑，風險程度不同。

### 2.2 情況 A：只蒸餾風格與結構規律（風險低）

女媧 Skill 蒸餾方法論的做法，是把大量素材拿去萃取「心智模型、決策啟發式、表達 DNA」等抽象規律，最終寫入 SKILL.md 的是**規則描述**（例如：慣用「按…定有明文」作為法條引用開頭、事實與理由段落遵循法理三段論推進），而不是判決書原文本身。

在這種模式下，Agent 讀到的是「這類文書該怎麼寫」，不是「某個具體案子法院判了什麼」。因為蒸餾出來的內容已經被抽象化、去案例化，Agent 對任何單一判決書並不存在可追溯的「記憶」，污染風險低。

### 2.3 情況 B：把完整判決書當 Few-shot 範例塞進 Prompt（風險高）

如果為了讓 Agent 學會攻防邏輯或訴狀寫法，直接把數十份完整判決書放進 System Prompt 作為範例，情況就不同了，會產生兩層問題：

**(1) 錨定偏誤（Anchoring Bias）**
Agent 容易把新輸入的案件事實「套用」進它記得的舊案模式，即使新案件的關鍵事實不同，也可能因為表面相似而產生錯誤類比，導出不精確的攻防策略或法律適用結論。

**(2) 資料污染（Data Contamination）**
這是更嚴重、且容易被忽略的問題。如果日後要用「這批判決書」來測試攻防系統的準確度（例如：拿判決書的事實描述去跑攻防模擬，看預測結果跟法院實際判決是否吻合），但這些判決書本身早就被塞進 Prompt 讓 Agent「看過」，那麼測試結果會失真——這如同讓學生拿已經背過答案的考卷去驗收學習成果，分數會好看，但完全無法反映系統的真實推理能力。這會直接摧毀第三章要建立的自動化驗證機制的可信度。

### 2.4 建議架構：蒸餾與檢索分離

為同時保留蒸餾的表達品質優勢，又避免記憶污染，建議採取以下分離原則：

| 階段 | 素材處理方式 | 是否長駐 Prompt |
|---|---|---|
| **蒸餾階段**（建構 Skill） | 萃取結構、語氣、三段論邏輯等抽象規則，寫入 SKILL.md | 是，但內容已去案例化 |
| **生產階段**（實際攻防與生成） | 需要案例佐證時，透過 RAG 即時檢索相關判決片段 | 否，用完即丟，不長駐於系統 Prompt |
| **驗證階段**（測試系統準確度） | 使用**未曾被蒸餾或檢索污染過**的判決書作為獨立測試集 | 不涉及，僅作為外部評分基準 |

核心原則：**蒸餾只萃取「怎麼寫」，不記憶「判了什麼」；需要案例佐證時用 RAG 即時查、即時丟，不長期駐留在 Prompt 記憶中；驗證用的判決書必須與訓練/蒸餾用的判決書完全隔離，才能確保測試結果的有效性。**

## 三、問題二：如何低成本驗證攻防與訴狀產出資料的價值

### 3.1 核心洞察：判決書本身自帶「標準答案」

一般機器學習專案要驗證模型輸出品質，往往需要額外聘請專家標註資料，這正是使用者原本擔心的額外開銷。但本專案有一個結構性優勢：**法院已經對每一份判決書做出了最終認定——誰勝訴、賠償金額多少、法院採信哪一方的論點、依據哪些法條——這些資訊全部已經寫在判決書裡。**

這代表不需要另外聘請律師「重新評分」，可以直接把真實判決結果當作自動化驗證的基準點（ground truth），用「系統預測」對比「法院實際結果」的落差，來衡量系統產出的價值。

### 3.2 分層驗證機制（成本由低至高）

#### 3.2.1 結果準確率（完全自動、零成本）

將判決書中的「事實描述」部分抽取出來，餵給攻防系統跑一輪模擬對抗，記錄系統預測「誰勝訴、賠償金額區間」的結果，再與判決書實際結果比對，計算準確率。此指標完全由程式自動計算，不需任何人工介入。

#### 3.2.2 爭點命中率（自動、零成本）

台灣判決書通常會明確列出「本院爭點如下」的段落，這段文字本身就是法院官方認定的標準答案。將攻防 Agent 自行分析出的爭點清單，與判決書中法院實際認定的爭點做文字比對，計算命中率。命中率越高，代表攻防引擎抓爭點的能力越貼近真實司法實務判斷，此指標同樣不需要法律專業人工判斷，屬於文本比對層級的自動化作業。

#### 3.2.3 引用真實性檢查（自動、零成本）

針對攻防過程與訴狀產出中引用的法條編號、判例字號，透過程式化方式比對官方法規資料庫與司法院判決書系統，確認引用是否真實存在、內容是否吻合。這與 Lawsnote 對外強調的「RAG 消除幻覺」屬於同一思路，純屬資料比對工程，不涉及法律專業判斷，可完全自動化執行。

#### 3.2.4 LLM-as-judge 雙盲互評（低成本，非人工）

女媧 Skill 專案本身在驗證蒸餾品質時，採用的方法是讓兩個獨立的 AI Agent 進行雙盲互評，依據多個維度（例如：立場一致性、風格辨識度、來源透明度、結構完整度）評分，而非依賴人工審核。本專案可比照設計一套針對「攻防品質」與「訴狀專業度」的評分維度，指派另一個獨立的 LLM 角色擔任裁判，大量批次執行，邊際成本趨近於零，且可規模化套用在任意數量的案件上。

#### 3.2.5 邊界案例真人律師抽樣校準（小成本，僅在必要時使用）

前四層機制皆完成後，會篩選出「自動化指標顯示異常」或「LLM 雙盲互評分數落在中間地帶、難以判斷」的少量樣本。只有這批經過層層過濾後、真正具有爭議性的邊界案例（預估數量約為總樣本的 5%~10%），才需要送交真人律師審核。這種做法將原本「全樣本人工審查」的高成本，壓縮成「僅審查疑難樣本」的低成本模式，同時仍保留人工專業判斷作為最終品質守門機制。

### 3.3 成本效益總結

| 驗證層級 | 判斷依據 | 是否需人工 | 邊際成本 |
|---|---|---|---|
| 結果準確率 | 判決書實際勝負結果 | 否 | 趨近零 |
| 爭點命中率 | 判決書「本院爭點」段落 | 否 | 趨近零 |
| 引用真實性檢查 | 官方法規/判決資料庫比對 | 否 | 趨近零 |
| LLM 雙盲互評 | 獨立 LLM Agent 評分 | 否 | 低（API 成本） |
| 邊界案例校準 | 真人律師審核 | 是 | 低（僅抽樣 5%~10%） |

## 四、綜合建議與後續執行步驟

1. **蒸餾階段嚴格遵循「去案例化」原則**：SKILL.md 中只保留結構、語氣、邏輯規則，不嵌入完整判決書原文，確保 Agent 不對特定案例產生記憶依附。
2. **建立獨立測試集，與訓練/蒸餾語料完全隔離**：預留一批從未進入蒸餾或 RAG 檢索流程的判決書，專門用於驗證階段，避免資料污染導致驗證結果失真。
3. **優先建置全自動驗證管線（3.2.1～3.2.3）**：這三項指標完全不涉及主觀判斷，屬於工程可解決問題，應在系統開發早期即納入 CI/CD 流程，每次系統迭代都能自動跑出量化分數。
4. **導入 LLM-as-judge 機制取代大規模人工審核**：參考女媧 Skill 已驗證有效的雙盲互評方法，作為介於「純自動化指標」與「真人律師審核」之間的品質守門層。
5. **將律師諮詢資源集中在邊界案例**：只在自動化與 LLM 評分機制皆無法明確判斷的少量疑難樣本上，才引入真人律師時數，將原本可能高昂的人工審核成本壓縮至可控範圍內。
