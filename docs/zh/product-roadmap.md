## 一、現況基準點(2026-08-08)

在規劃未來之前,先誠實盤點現在站在哪裡——這份基準點是後面所有階段判斷的錨。

### 1.1 產品定位(已定案,不再變動)

- **絕不做 B2C**:《律師法》§127 對非持照民眾收費代寫訴狀屬刑事風險,免責聲明無法免除。
- **產品重心是「爭點提出/整理者」,不是「模擬開庭/預測判決」**:R1→R2→R3 多輪攻防(盲判→強制反駁→falsifier)是核心價值引擎,目的是逼出多角度爭點、強迫雙方正面對決;法官角色輸出是「爭點強弱評估與訴狀優先順序建議」,不是判決預測。爭點分析可以講得篤定,涉及結果預測的表述一律避免。
- **訴狀生成是攻防預演的副產品,不是主賣點**(2026-08-08 因 Donna 查證而強化的判斷,見 1.3)。

### 1.3 已知的強訊號與缺口

**強訊號**:三案測試中,原告方在 `test-2026-08-08-001` 案主動核對對造引用的判例全文,發現對造援引的判決「案由完全不符」(誤用引用),成功削弱對造論點——**這是「對抗協議抓到單一LLM彙整抓不到的問題」的第一手工程證據**,雖然不是律師本人的評估,但比空談更有份量。案三也出現一次單一提示詞版本結構上做不出來的來回交鋒。

**缺口**:
- 查證引擎在測試過程中抓到過兩個真實 bug(子條文「之N」被誤判成完全不同條文、民事訴訟法原本未涵蓋)——說明「零容錯」不是一次寫完就穩了,需要持續用真實案件壓測才找得到這類靜默錯誤。
- 溫度控制(AgentCourt 借鏡的 0.7/0.2)因 Claude Code 派工機制限制無法真正落實,已誠實記錄為已知限制,技術上可解但要轉向直接 API 呼叫架構(見中期規劃)。
- **律師管道仍是唯一真正卡住的資源**,同時堵住訴狀語料(Phase 0)跟真人驗證(Phase 2)兩件事。
- **✅ 已修正(2026-08-09)**:`stage1_prompt.txt` 引用來源邏輯已改正(不論本地語料庫有無命中,皆先依自己法律知識列出候選引用,Grep 僅作平行補充來源,挑選標準是構成要件貼切度而非本地查得到與否),並在 Step 8 新增對最終採用引用的實質查核(案由/爭點是否真的支持論點,延伸自 Stage2/3 既有的對造引用查核鐵律)。詳見 `.claude/skills/legal-debate/SKILL.md` 已知限制章節。
- **已識別但暫緩(2026-08-08)**:現有 3 案內部測試的「單一LLM基準」是裸提示(無RAG、無主動查核引用實質的指示),對照組偏弱,只能證明「贏過完全沒結構的提示」,不能證明贏過 LawBotAI 深度探索這類 LLM+RAG+多步驟彙整的單一 Agent 對手。更嚴謹的做法是加測第三組基準:「單一 Agent + RAG + 明確要求批判性查核引用實質」,以判斷本產品的優勢究竟來自對抗協議本身,還是只來自「有結構化查核步驟」這件事(若是後者,代表真正該賣的可能是更便宜的單一Agent查核功能,不需要整套四階段協議)。**因需另建 RAG 查核 pipeline 作為對照組,實作成本偏高,先記錄,暫緩執行**,待資源許可或有更迫切的驗證需求時再排入。

### 1.4 競品格局(五家已查證,無人做真正的雙方對抗攻防)

| 競品 | 佔據的層次 | 對本案的意義 |
|---|---|---|
| Lawsnote | 法學資料庫+CLM,市場龍頭 | 記錄層紅海,不打 |
| LawBotAI | 記錄層+單一模型推理層(「深度探索」已付費驗證需求) | 證明推理層有付費意願,但也證明「推理」這個詞本身已不是差異化 |
| TaiLexi AI | 純記錄層,免費增值 | 印證記錄層轉換率結構性低,不是本案的商業模型 |
| LegalSign.ai(律果科技) | 合約管理,不同垂直 | 非同軸競品 |
| Donna | 律師事務所案件管理(Legal Ops),AI為嵌入助理 | **唯一真正碰到「案件理解/資料整理」這一層的成熟對手**,其儲存中立+BYOK架構值得借鏡 |

**結論(逐一查證後不變)**:「AI vs AI 雙方獨立對抗辯論(盲判→強制反駁→falsifier→爭點強弱評估)」這個窄協議層級,商業產品層級依然查無直接對手。但「記錄層」「單一模型推理層」「案件管理層」三個相鄰層次都已經有成熟玩家,代表**本案的差異化必須嚴格收在對抗協議本身,不能靠功能廣度取勝**。

## 二、短期(現在 → Phase 2 完成,產品仍是內部 CLI 工具)

### 2.1 這個階段要回答的唯一問題

**核心攻防協議(R1→R2→R3)產出的爭點分析,是否明顯優於一次性問單一 LLM 的結果,優到值得律師多付錢?**

在這個問題有明確答案之前,任何功能擴張都是分散資源。

### 2.2 產品規劃

| 項目 | 內容 |
|---|---|
| **目標用戶** | 1-2 位友好持照律師(Design Partner),非公開產品 |
| **產品形態** | CLI + Claude Code orchestrator skill,無網頁介面,無公開帳號系統 |
| **核心功能範圍(要做)** | 三角色民事通常訴訟攻防(已完成)、骨架版訴狀初稿(已完成)、爭點強弱評估(已完成);**新增候選**:輕量案件輸入前處理——律師貼一段案情文字,跑一次 LLM 呼叫轉成 `Case` schema 結構化欄位,降低 Design Partner 測試時「先手打 JSON」的摩擦(見 2.4) |
| **核心功能範圍(明確不做)** | 完整案件理解層(時間軸/當事人關係圖/證據庫自動建檔)、卷宗 PDF 上傳與管理、律所案件管理(行事曆/報稅/工時/收發文)——這些是 Donna 的地盤,現階段做了也無助於回答本節核心問題 |
| **定價假設** | 免費(Design Partner 性質,尚未商業化) |
| **成功門檻(進入中期的 go 訊號)** | 至少 1 位真實律師完成 D 段盲測(單一LLM提示 vs 本產品四階段輸出),明確表態哪個更有幫助且說得出具體理由;或至少對 3-5 個真實/接近真實的案件跑出「單一LLM抓不到、本產品抓到」的具體案例(如已發生過的引用案由不符) |
| **主要風險** | 律師管道持續打不開,導致這個階段被無限拖長 |

### 2.3 律師管道是本階段唯一真正的優先項

Phase 0(訴狀語料)與 Phase 2(真人驗證)卡在同一個瓶頸——不是工程問題。按 `Phase2_律師訪談問題清單.md` 已設計的訪談框架,搭配已討論過的替代/降級手段同步進行,不要等到「湊齊條件」才開始:

1. **持續累積自我驗證訊號**(不需要律師也能做):比照已完成的 3 案測試,擴大案類覆蓋(繼承、租賃、票據等),每案記錄是否再次出現「對抗協議抓到單一提示抓不到」的具體案例,建立內部案例庫。
2. **二手資料與群眾外包降低對正式訪談的依賴**:Dcard 法律人版等既有社群討論(受限於平台反爬蟲,需人工瀏覽)、App Store/Google Play 評論、公開盲測投票——用來校準 C 段(付費意願錨定)與 B 段(競品使用經驗),把最稀缺的真人資源留給 D 段盲測與訴狀語料。
3. **輕量人脈嘗試不設門檻**:認識的學長姐、朋友介紹的律師,不必是正式邀約的 Design Partner,一次非正式的意見交換也能推進 D 段盲測。

### 2.4 「輕量案件輸入前處理」是本階段唯一可以採納的擴張

這是從 `AI律師案件工作平台_產品願景與系統概念.md` 的 Stage 1(案件理解)萃取出來、經過大幅降規格後的版本:**不是**時間軸/當事人關係圖/證據庫這種完整結構化案件模型,**只是**「貼一段案情文字 → 一次 LLM 呼叫 → 產出 `Case` schema 需要的欄位」。這個範圍刻意畫得很小,理由:

- 現在的輸入方式(律師手打 JSON)對 Design Partner 測試是真實的摩擦,值得降低。
- 但完整版的「案件理解」是 Donna 已經做得很成熟的功能(100頁卷宗30秒抓重點、自動歸檔),重建它既貴又打不過既有玩家,對回答本階段核心問題(協議是否有效)沒有幫助。
- 這個輕量版本本身工程成本低(一次 LLM 呼叫+ schema 驗證),不會拖慢 Phase 1.5/2 的進度。

## 三、中期(Phase 2 訊號出現 → Phase 3 判斷 + 早期商業化,產品可能開始有網頁前端)

### 3.1 觸發條件

進入這個階段的前提是短期階段已經拿到至少一個真人(即使只是非正式接觸)的明確回饋,而非日期到了就自動推進。

### 3.2 產品規劃

| 項目 | 內容 |
|---|---|
| **目標用戶** | 3-5 個穩定 Design Partner 律所,仍非公開產品 |
| **產品形態** | 視 Phase 2 回饋決定是否需要離開純 CLI——若律師覺得指令列操作門檻太高,才考慮輕量網頁前端(比照 「DebateSystem-Web 專案」(內部知識庫頁面,未隨本 repo 發布) 的既有模式);若 CLI 已可接受,不必為了「看起來更產品化」而提前做 UI |
| **核心功能範圍** | `taiwan-legal-pleading` Skill 首次蒸餾(語料到位後)、訴狀語氣潤飾、依 Phase 2 回饋精修 stance_rag 用詞與法官 prompt;**Phase 3 是否啟動見 3.3** |
| **定價假設** | 開始討論但不急著拍板;已有的市場定價點——LawBotAI Lite/Pro(NT$480-1,000/月,推理層功能內含於同一訂閱)、Donna(token+儲存分開計費,3M token NT$1,500/月起,全所不限人數)——都指向「額度制」比「無限吃到飽」更貼近業界常態,已初步討論的 credit/用量額度制方向可作為基礎,實際數字待 Phase 2 訪談 C 段的付費意願錨定結果 |
| **成功門檻** | 3-5 個律所產生 30+ 件真實案件的爭點覆蓋率回饋數據(見護城河里程碑B);若持續無法取得穩定 Design Partner,重新評估是否要下修到「先服務 1 位律師做深度打磨」 |
| **主要風險** | 定價定得比市場基準高卻沒有相應的溢價證明;或反過來定得太低,重演 TaiLexi「功能到位但月營收打不平」的軌跡 |

### 3.3 Phase 3(防套皮強化:資訊不對稱切面+異質模型矩陣)go/no-go

**不整包提前**,拆兩個子項分開判斷:

- **異質模型矩陣**(原告/被告/法官跑在不同供應商):這是回應「同一顆大腦戴面具」疑慮最直接的機制。架構上現在(1.4 已完工)才發現溫度控制受限於 Claude Code 派工機制,若中期階段真的要做網頁產品,後端本來就需要直接呼叫 Anthropic/OpenAI/DeepSeek 的 Messages API(不能讓網頁請求觸發 Claude Code subagent)——**溫度控制與異質模型矩陣可以是同一次架構轉向的兩個附帶產出,不需要為了單一目的提前做**。觸發訊號:Phase 2 律師實測觀察到「雙方論點趨於雷同」。
- **真正的資訊不對稱切面**(檢索層物理隔離,而非現在的「暫不顯示對方輸出」):成本較高且與「候選功能:語意向量RAG判例庫」(另一個獨立觸發條件——律師表達需要系統主動找有利判例)有工程依賴,不建議跟異質模型矩陣同時提前,優先度更低。

### 3.4 借鏡 Donna 的具體行動項(本階段適合排入)

- **儲存中立 + 自帶 API 金鑰(BYOK)**:案件資料留在律所自己的雲端,律所自帶 Anthropic/OpenAI/Gemini API key。直接解掉「四大死穴」死穴3(律所抗拒資料上公有雲,需私有部署)——用架構設計取代真正蓋私有部署,成本低很多;同時緩解死穴4(單次辯論 NT$50-100 的成本由律所自己的 API 帳單吸收,不侵蝕本專案毛利),也讓 3.3 的異質模型矩陣更容易落地(律所可能已有多供應商帳號)。
- **卷宗引用可回溯頁碼**:現在的零容錯查證引擎只查證公開法規/判例,沒有涵蓋原告/被告/法官引用**案件卷宗本身**(筆錄、證據)時的可追溯性。這是查證引擎的實質缺口,應在律師開始用真實卷宗測試前補上。
- **永久指令(律所自訂持久化偏好)**:輕量版的「律所辦案風格客製化」,不需要真正的 DNA 蒸餾管線,可作為長期護城河里程碑D的低成本前導版本提前驗證需求。

### 3.5 護城河建設啟動(對應 `競爭優勢與護城河建立策略報告.md`)

- **里程碑A**:爭點覆蓋回饋機制雛形(律師開完庭回來勾選:覆蓋/漏抓/優先序判斷落差),前提是已有穩定律師關係——與本階段的 Design Partner 拓展同步進行,不是獨立項目。
- **里程碑B**:累積 30+ 件真實爭點覆蓋率數據後,可先在 Design Partner 對話中佐證使用;是否公開透明頁面需先評估法律/行銷用語風險(不可暗示判決預測能力)。

## 四、長期(Phase 4+,商業分岔階段,高度視前面訊號調整,不是固定時間表)

長期規劃的不確定性最高,這裡只標出決策分岔點與各分岔下的合理路徑,不假裝能預先排出精確時程。

### 4.1 分岔一:台灣 B2B 深耕 vs 全球 Common Law/YC

已有分析(見知識庫 「新創評估框架五步驟」(內部知識庫頁面,未隨本 repo 發布) 附錄四、「LegalDebate AI」(內部知識庫頁面,未隨本 repo 發布) YC申請可行性補充):
- 台灣路線:B2B 訂閱制推廣中小型律所,天花板約年營收千萬元級,但護城河(數據飛輪/Track Record)可在地累積。
- 全球路線:美國市場 TAM 大但資本密集紅海(Harvey AI 估值 $1.5B+)、資料寡佔(Westlaw/LexisNexis)、UPL 執照問題換馬甲依舊存在;台灣驗證只能作為方法論可行性證明,語料/蒸餾資產不可直接跨法域移植。
- **這個分岔的決策時機是 Phase 2/3 之後**,不是現在,但長期規劃需要預先承認:選了全球路線,台灣階段累積的護城河資產大部分要重新來過。

### 4.2 分岔一之下的護城河里程碑C/D(僅適用於台灣路線,或全球路線的在地化階段)

- **里程碑C(Word/Google Docs 插件)**:讓律師不用離開撰狀環境即可呼叫攻防分析,提高黏著度。技術上不難,但需要重新設計產品體驗,建議在有穩定付費客戶後才投入。
- **里程碑D(律所客製化辦案風格DNA蒸餾)**:長期最高切換成本的護城河,需要 5-10 個穩定客戶累積使用資料後才有意義,前導版本見 3.4 的「永久指令」。

### 4.3 分岔二:刑事模式擴充

四階段 SOP 目前僅限民事三角色(原告代理人/被告代理人/法官)。刑事模式(檢察官/辯護人/合議庭)明確列為範圍外,啟動時機取決於民事版本商業驗證是否成立,不是技術準備度的問題——刑事案件的攻防邏輯與量刑因子跟民事完全不同,等於重新蒸餾一套角色 Skill。

### 4.4 分岔三:是否真的要往「AI Legal Case Workspace」方向擴張

這是 `AI律師案件工作平台_產品願景與系統概念.md` 提出的長期願景,本報告的立場是:**方向本身不否定,但不是現在,而且執行方式很可能不是「自己重建」**。

- **不建議走的路徑**:自建完整案件管理層(卷宗上傳/OCR/PDF標註/時間軸UI/多雲端同步)——這正是 Donna 已經做得成熟的地盤,一個資源有限的團隊在核心攻防協議都還沒充分驗證增值的階段就去打這場仗,是資源分散的錯誤決策。
- **較合理的路徑**:若核心攻防協議充分驗證有價值、且已有穩定客戶基礎,優先考慮與 Donna 這類案件管理平台做 API 層整合(LegalDebate 作為可掛載的推理模組),而非正面重建。這與 4.1 分岔一的定位也是一致的——本產品的護城河賭注押在「攻防推理有沒有價值」,不是「案件管理做得完不完整」。
- **什麼情況下才重新考慮自建**:Donna 或同類玩家出現明確的產品/商業危機(例如關閉、轉型),或核心攻防協議驗證出的價值大到足以支撐一輪能負擔完整平台開發的資金,兩個條件出現任一個才重新評估,不是願景稿寫得動人就啟動。

### 4.5 長期敘事保留(從願景稿萃取,價值在講故事而非執行規劃)

以下三句定位語從 `AI律師案件工作平台_產品願景與系統概念.md` 保留,作為長期融資/對外溝通時的敘事素材,對應 4.4 的「不是現在但方向不否定」立場,直接回應 YC 申請報告裡已點名的「70% wrapper 淘汰率」風險——用「workflow/protocol/evaluation system」的敘事,而非「AI 寫書狀按鈕」:

- 對律師:「不是幫你寫一份書狀,而是幫你把一個案件的爭點分析、攻防推演前置工作做完。」
- 對投資人:「We are building an AI-native legal reasoning workflow that transforms document-centric legal work into an agentic, verifiable process.」(已從原稿的「case workspace」修正為聚焦「reasoning workflow」,避免暗示與 Donna 等案件管理平台正面競爭)
- 對未來:「AI 不取代律師,而是成為每一位律師背後的一支 AI 辦案團隊。」
