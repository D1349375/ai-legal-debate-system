## 一、執行摘要（Executive Summary）

本專案旨在將團隊現有的兩大技術底層——**Startup Guide 的「零容錯內容查證體系」** 與 **DebateSystem 的「多 Agent 結構化辯論引擎」** 進行深度結合，並導入 **女媧（Nuwa）Skill 蒸餾技術** 萃取台灣裁判書與專業律師之「法言法語與訴狀默認寫法 DNA」。

本系統不單純提供模板填空，而是**在訴狀生成前，讓「原告律師 AI」與「被告律師 AI」針對案件糾紛進行結構化攻防演練**，抓出合規漏洞與對手潛在死穴，最終產出具備專業律師水準之起訴狀、答辯狀與存證信函初稿。

> **本文件於 2026-08-06 依三份技術附錄（RAG 系統設計、自建法學資料庫、YC 投資調研）之審視結果更新**，核心判斷標準統一為**台灣律師是否願意且能夠使用**，非投資人評分標準。詳細變更理由見 [`新增文件整合規劃報告.md`](./新增文件整合規劃報告.md)。

## 二、核心技術架構與三引擎融合

本系統由三大核心模組構成，解決傳統 LegalTech 工具「容易產生 AI 幻覺（編造法條）」與「文字欠缺專業度」之兩大痛點：

```
                    [ 用戶輸入：糾紛經過 / 合約 PDF / 證據清單 ]
                                         ↓
┌────────────────────────────────────────────────────────────────────────┐
│ 1. 知識與零容錯查證引擎（基於 Startup Guide 體系）                        │
│    • 台灣現行法規庫：民法、公司法、勞基法、消保法、刑法條文檢索         │
│    • 實務判例庫：司法院最高法院真實判例/裁判字號檢索                    │
│    • 機械化防幻覺稽核：100% 驗證法條有效性與判決字號真實性               │
└────────────────────────────────────────────────────────────────────────┘
                                         ↓
┌────────────────────────────────────────────────────────────────────────┐
│ 2. 多 Agent 模擬攻防引擎（基於 DebateSystem 體系）                       │
│    • 原告律師 Agent：尋找最有利主張、求償依據、請求權基礎               │
│    • 被告律師 Agent：尋找免責條款、程序瑕疵、對方舉證漏洞               │
│    • R1 獨立盲判 → R2 結構化反駁：產出案件爭點與「最脆弱死穴清單」        │
└────────────────────────────────────────────────────────────────────────┘
                                         ↓
┌────────────────────────────────────────────────────────────────────────┐
│ 3. 專業訴狀蒸餾生成引擎（基於 女媧 Skill 蒸餾體系）                      │
│    • 載入 `taiwan-legal-pleading` Skill（涵蓋法院默認習慣與法言法語）   │
│    • 訴之聲明精準化（利息、違約金、管轄法院完整標註）                    │
│    • 事實與理由三段論（法律依據前置 → 事實歸入 → 結論）                  │
└────────────────────────────────────────────────────────────────────────┘
                                         ↓
                    [ 最終輸出：案件攻防評估報告 + 合規起訴狀初稿 ]
```

> **Engine 1 技術風險補充**：台灣判決書「按…定有明文」「查」等高度制式化行文，容易觸發「文件層級檢索錯配（DRM）」——檢索抓到的是內容相似但完全錯誤的來源判決書，實測此類錯誤率可超過 95%。這是 Engine 1 的**首要**技術風險，而非「機械化防幻覺稽核」一句話能涵蓋，須以摘要增強分塊法（SAC）等具體工程手段處理。完整規格見 [`RAG系統設計報告_學術基礎與產品實作規格.md`](./RAG系統設計報告_學術基礎與產品實作規格.md)。

## 三、訴狀 Skill 蒸餾機制（`taiwan-legal-pleading`）

針對法律系與實務律師強調之「不成文訴狀寫法習慣」，運用女媧 Skill 蒸餾技術進行語言 DNA 萃取：

### 1. 語料來源（Corpus）
- 司法院公開判決書之原告/被告主張精華
- 司法院官方標準書狀範例
- 律師公會與知名訴訟律師公開之起訴狀與答辯狀

### 2. 蒸餾出的三大領域 Know-How
- **訴狀結構骨架（Structural Heuristics）**：
  明確區分「訴之聲明」、「請求權基礎」、「事實與理由」、「證據清單」，且「事實與理由」嚴格遵循法理三段論推進。
- **法言法語表達 DNA（Expression DNA）**：
  採用正統連接詞與開頭（如 `按...定有明文`、`次查...`、`再查...`、`揆諸前揭最高法院判例意旨...`），避免白話文或翻譯腔。
- **避坑與法院禮儀規範（Negative Rules）**：
  自動將情緒化用語校正為法律專業修辭（如將「對方無恥不還錢」修正為「被告所辯顯係推諉卸責之詞，殊無足採」），並確保標註管轄法院與訴訟標的金額。

### 3. 蒸餾與檢索分離原則（風險控制，必要）
蒸餾階段**只萃取「怎麼寫」的抽象規律，不記憶「判了什麼」**——SKILL.md 中只保留結構、語氣、三段論邏輯規則，不嵌入完整判決書原文。若把完整判決書當 few-shot 範例塞進 Prompt，會導致 Agent 對舊案產生錨定偏誤，且會污染日後用同一批判決書驗證系統準確率的測試結果（如同學生拿背過答案的考卷驗收）。因此蒸餾語料、RAG 即時檢索語料、驗證測試集三者須完全隔離。詳見 [`自建法學資料庫_蒸餾污染風險與資料價值驗證機制報告.md`](./自建法學資料庫_蒸餾污染風險與資料價值驗證機制報告.md)。

## 四、端到端使用者體驗流程（User Journey）

1. **資訊輸入**：用戶輸入糾紛經過白話描述，並上傳相關合約 PDF 或對話截圖。
2. **法理與判例匹配**：系統自動調取台灣現行法條與相關最高法院判例（Startup Guide 查證模組）。
3. **AI 模擬攻防辯論**：
   - 原告 Agent 提論點 A；被告 Agent 根據免責條款進行 R2 反駁。
   - 系統標註出「本案最大的 2 個舉證弱點」與「建議補充之證據」。
4. **專業訴狀生成**：調用 `taiwan-legal-pleading` Skill，15 秒內生成符合司法院格式之 Word/PDF 起訴狀或存證信函初稿。

## 五、商業化與變現模式分析

商業化分為 B2C（平民/中小企業）與 B2B（律師事務所/企業法務）兩大路徑：

### 1. B2C 模式（民眾/中小企業老闆）
- **定位**：平民的法律預審與訴狀初稿生成工具。
- **定價**：按次付費（如 **NT$999 / 案**）或諮詢包。
- **產出**：【案件勝率與爭點分析報告】＋【標準起訴狀 / 存證信函初稿】。

### 2. B2B 模式（律師事務所 / 企業法務部）
- **定位**：資深律師的「攻防腦力激盪 ＋ 實習律師起草 Copilot」。
- **定價**：SaaS 月費訂閱（如 **NT$3,000 – NT$9,999 / 律師 / 月**）。
- **價值**：幫律師在 10 分鐘內完成開庭前之雙向攻防模擬與訴狀初稿，節省 70% 撰寫時間。

## 六、最嚴苛的法律與商業風險評估（Brutal Risk Assessment）

拋開樂觀幻想，本專案在落地時必須面對 **四大致命死穴**：

### ⚠️ 死穴一：台灣《律師法》第 127 條刑事死穴（最高風險）
- **法規紅線**：《律師法》§127 明定「無律師證書，意圖營利而辦理訴訟事件或撰擬訴狀者，處 **3 年以下有期徒刑，併科 50 萬元以下罰金**」。
- **實務風險**：若對 B2C 一般民眾收費並提供訴狀生成，**律師公會極大機率會主動檢舉告發**。免責聲明在司法實務上無法免除刑事責任。
- **解法**：**放棄 B2C 對外收費**；僅做 B2B 賣給「持有執照的律師」作為內部工具，或作為律所合夥之技術後台（100% 合法）。

### ⚠️ 死穴二：B2C 單單位經濟學（Unit Economics）崩塌
- **LTV 極低**：一般民眾一輩子打官司的次數為 0~1 次，留存率（Retention）幾乎為 0%，無法形成訂閱制。
- **CAC 極高**：Google 搜尋「起訴狀 代寫」、「律師諮詢」競價極度昂貴（單次點擊 NT$50~200）。
- **結論**：B2C 獲客成本 (CAC) 遠大於 顧客終身價值 (LTV)，商業模型不成立。

### ⚠️ 死穴三：B2B 銷售難度與資安疑慮
- **資安與保密 (NDA)**：律師事務所處理客戶機密，極度抗拒將資料傳至公有雲 API，需提供私人部署（Private VPC）或高階資安認證。
- **市場天花板限制**：全台灣執業律師僅約 1.2 萬人。若渗透率 2%（240 人），月營收上限約 **NT$72 萬 / 月**。

### ⚠️ 死穴四：事實認定 (Fact Finding) 與 Token 成本
- **勝負在於證據**：AI 能辯論法理，但無法替用戶採集實體證據。若輸入之事實不完整（Garbage in），攻防與訴狀亦為 Garbage out。
- **Token 消耗**：多 Agent 辯論 ＋ 判例檢索單次消耗 30~50 萬 tokens，單次 API 成本達 **NT$50~100**。
- **產出品質怎麼驗證（補充）**：不需要聘律師全樣本審核——判決書本身已寫明誰勝訴、賠多少、爭點為何，可直接當 ground truth 做自動化比對（結果準確率／爭點命中率／引用真實性），僅將自動化指標篩出的 5-10% 邊界案例交真人律師審核。此為**選配的附加功能**，非產品上線之必要條件，但能加速取得律師設計夥伴的初始信任。詳見 [`自建法學資料庫_蒸餾污染風險與資料價值驗證機制報告.md`](./自建法學資料庫_蒸餾污染風險與資料價值驗證機制報告.md)。

## 七、評估結論與戰略執行路線圖

### 最終商業判決
1. **絕不做 B2C 大眾收費訴狀網站**：避免觸犯《律師法》§127 刑事責任與高昂 CAC 陷阱。
2. **核心目標是台灣 B2B 市場**：定位為律師內部的輔助工具，能否被台灣執業律師實際採用是唯一驗收標準，市場天花板在年營收千萬元上下屬已知限制、非需優化項。
3. **全球化與對外募資屬選配路徑**：技術上可行，但蒸餾出的法言法語 DNA 與 RAG 資料庫綁定台灣司法管轄區，移植至美英法系需重新蒸餾、重建資料庫，等同另一工程專案，非「沙盒驗證後可直接適配」；僅在台灣市場站穩、且有意願時才需評估，詳見 [`YC投資調研報告.md`](./YC投資調研報告.md)（僅供募資參考，非核心開發標準）。
